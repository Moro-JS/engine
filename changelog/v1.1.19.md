# @morojs/engine 1.1.19

HTTP/2, a cheaper TLS write path, request bodies that no longer drive V8 into
back-to-back full collections, and an epoll fix for loops with thousands of
ready sockets.

Additive for existing callers: one serve option (`http2`), three exports
(`getBodyType`, `getBodyText`, `getBodyLent`), three capability flags
(`http2` now true, `bodyText`, `bodyLent`). One default changes on the wire:
with no `ssl.ciphers` / `ssl.ciphersuites`, a client that offers both is now
given AES-128-GCM rather than AES-256-GCM (below).

## HTTP/2

`serve()` option `http2`: `true`, or the settings to advertise
(`maxConcurrentStreams`, `initialWindowSize`, `maxFrameSize`,
`maxHeaderListSize`, `headerTableSize`). A TLS listener offers `h2` ahead of
`http/1.1` in ALPN; a cleartext listener speaks HTTP/2 to a client that opens
with the connection preface (prior knowledge) and HTTP/1.1 to every other,
on the same port.

It is the engine's own implementation of RFC 9113 and HPACK (RFC 7541), in
`src/http2.h`: a pure state machine like the HTTP/1 parser, with no I/O and
no V8 in it. The roadmap had planned a vendored nghttp2. Writing it here
means nothing third-party to track, and an HPACK encoder that keeps no
per-connection state, so the header block of a prepared response is encoded
once and replayed on every connection.

A request arriving on a stream is delivered exactly as an HTTP/1 request is:
the same `onRequest` / `onRequestBatch`, the same accessors, the same
`respond` / `writeHead` / `write` / `end`, static and parameter routes,
prepared responses, the typed body reads. Pseudo-headers do not reach the
application; `:authority` is delivered as `Host` when the request carried
none. Response headers written for HTTP/1 are sent as they are, lowercased,
without the ones that describe an HTTP/1 connection.

Requests completed by one read are handed to JS in batches of up to sixteen.
A handler that goes asynchronous does not hold up the ones behind it, as it
must on a pipelined HTTP/1 connection; the rest are delivered in another
call. Every frame produced while a read is processed leaves in one write.

What a peer can do without making a request is bounded: stream resets and
control frames draw on a per-connection budget (CVE-2023-44487), a header
block is bounded in bytes and in CONTINUATION frames (CVE-2024-27316), and
the server's existing limits apply per request (`maxHeadSize`, `maxHeaders`,
`maxBodySize`, `maxUriSize`). `docs/THREAT_MODEL.md` has the list. Closing a
connection resets the streams still open on it and says GOAWAY first;
`stopListening()` says GOAWAY and lets them finish.

Not served over HTTP/2: WebSocket (RFC 8441), server push, CONNECT.
Priorities are parsed and ignored.

Measured at one worker on one core with h2load (64 connections, 100 streams
each), through the MoroJS adapter, against the same application on Node's
`http2`:

| reply | Node http2 | engine |
|---|---|---|
| small text, cleartext | 46,400 req/s | 819,725 |
| small text, TLS | 39,712 | 765,250 |
| JSON, cleartext | 38,034 | 167,315 |

Verified with h2spec (146/146 over TLS; 145 on a cleartext port, where bytes
that are not the HTTP/2 preface are answered as HTTP/1.1), 1167 unit checks
including HPACK decoding against 647 header blocks from an independent
encoder, 23 end-to-end cases against `node:http2`, and a fuzz target run for
8.1 million inputs under ASan and UBSan.

## TLS: replies written straight to the socket

Found by profiling a 3 KB JSON reply and a 10 KB echo against a BoringSSL
server.

- The OpenSSL error queue is cleared only when it holds something.
  `ERR_clear_error()` resets all sixteen slots whether or not any is in use,
  three frees each, and ran before every read and write.
- No `SSL_read` for input known to be used up: that call could only report
  "want read", and to do so it allocated the record buffer it had just
  released and released it again.
- A reply's records go to the socket from OpenSSL's own record buffer when
  nothing is queued ahead of them, where they used to be copied to a scratch
  buffer and from there to the connection's buffer. A small record with more
  of the reply behind it (a head ahead of its body) leaves with the next one
  in a single `sendmsg`. Pipelined requests and WebSocket frames keep their
  batch.
- With no `ssl.ciphers` / `ssl.ciphersuites`, each AES-256-GCM suite is
  ordered behind the AES-128-GCM suite of the same key exchange and
  authentication, and ChaCha20-Poly1305 goes first for a client that lists
  it first. The set of ciphers is exactly what the linked OpenSSL and its
  policy provide; a client offering only AES-256 still gets it; an explicit
  list from the application is left alone. To keep the previous order, set
  `ssl.ciphersuites: 'TLS_AES_256_GCM_SHA384:TLS_CHACHA20_POLY1305_SHA256:TLS_AES_128_GCM_SHA256'`.

A 3 KB JSON reply over TLS at one worker: 15.9 to 14.7-15.2 us of CPU per
request.

## Request bodies: heap strings and lent buffers

`getBody()` returns an ArrayBuffer whose bytes live outside the JS heap. V8
counts such bytes against the old-generation limit from the moment they are
allocated until a collection frees them, so a server reading ten kilobytes
of body per request ran a full mark-compact every few thousand requests
however short-lived each body was: 79 in ten seconds of 10 KB echoes at one
worker, about 2.3 us of every request.

- `getBodyType(reqId)`: the Content-Type, `''` without one, `null` without a
  body. What an adapter needs to choose a read.
- `getBodyText(reqId)`: an all-ASCII body as a string - its exact bytes and
  its text - or `null`. An ordinary heap string, collected with the young
  generation.
- `getBodyLent(reqId)`: the body as an ArrayBuffer that is detached, and its
  bytes released, when the response completes or the request is aborted.
  Nothing is copied. JS may transfer the buffer to keep the bytes, and
  `getBody` during a loan returns a copy.

Body buffers are pooled per loop. A body used to be collected into
per-connection strings that kept their capacity, so every body was written
into memory untouched since that connection's last request and all of it was
held while connections sat idle. A connection that sends one request at a
time also reuses the same staged slot now, where its path and header strings
used to be spread over sixteen.

With the MoroJS adapter reading typed bodies, at one worker and 256
connections: mixed GET/POST 6.9 to 6.2 us of CPU per request; a 10 KB echo
over TLS with lent bodies 21.5 to 16.4, mark-compacts 79 to 5.

## Each ready socket served once per loop turn

The epoll transport records readable sockets in the poll phase and serves
them afterwards, grouped by peer CPU (1.1.12). Its watchers are
level-triggered and nothing is read while recording, so a socket reported
once is reported again by every further `epoll_wait` of the same turn - and
libuv waits again, up to 48 times, whenever a wait fills its 1024-event
buffer. A loop with more ready sockets than that queued each of them once per
wait and then called `recv()` on it that many times, all but the first for
`EAGAIN`, while the kernel re-polled a thousand sockets per wait to report
what was already known.

The turn's sockets are now served as soon as a full buffer's worth has been
recorded, which is when libuv is about to wait again, so the next wait
reports only what is new. A socket already served in a turn is not queued
again in it; level-triggered readiness repeats the report at the next turn
if bytes did arrive. Repeated reports of a socket still waiting for its
service are folded into its one entry.

Measured at one worker on one core with 4096 keep-alive connections:

| load | before | after |
|---|---|---|
| reply sent from a 10 ms timer | 14.7 us CPU/request | 7.1 - 7.4 |
| mixed GET / POST | 13.7 | 10.4 |
| `recvfrom` calls per request, timer load | about 13 | 1 |

Below 1024 ready sockets per loop turn nothing changes: a server spread over
many workers with a few hundred connections each was never affected, a
single worker holding thousands was.

Three regression tests hold 1500 sockets readable at once on one loop:
answered once each over repeated turns, with replies sent later from timers,
and with a second request arriving while the first wave is being served.
