# @morojs/engine 1.1.17

A TLS release. Nothing on the wire changes: the same records, in the same
order, from the same OpenSSL; what changes is how many times a byte is
touched between the socket and the record layer. No export or capability flag
is added, removed or renamed.

## The engine's own BIOs

The TLS session no longer runs on `BIO_s_mem` pairs. The read side is a view
over the buffer the transport just read: OpenSSL's record layer copies records
out of it, and that is the only copy on the way in; `BIO_s_mem` put a second
one, into its own buffer, ahead of it. The write side appends ciphertext
straight into the buffer the transport sends from, one append per record;
`BIO_s_mem` grew its own buffer by copying, was copied out of again, and then
zeroed its whole capacity on every reset, three passes over a large body on
top of the encryption, each paid again as fresh pages once the buffers were
freed between replies.

The ciphertext scratch is kept up to 1 MiB between replies instead of 64 KiB.
It is one buffer per loop, and releasing it after every large reply meant a
static file's worth of pages faulted in and zeroed again for each of them.

## Large bodies encrypted where they are

A TLS reply whose body is over 8 KiB is encrypted from the caller's bytes: the
head is built in the connection's scratch, the body is passed to `SSL_write`
as it is, and both land in the one ciphertext buffer the transport sends in
one write. The frame used to be assembled whole in scratch first, whose
capacity was then released again, so a large static file paid a plaintext
copy and fresh pages per reply. A small body still rides the head's record:
one copy of a few kilobytes costs less than a record of its own.

Measured against 1.1.16 at one worker, same machine, CPU per request from the
container's cgroup under the HttpArena request mixes over TLS: the static
file mix (eight to three hundred kilobytes, precompressed sidecars) from
39 µs to 31; the JSON mix (one to eight kilobytes) from 22 µs to 19; a 100 KiB
POST echoed back from 150 µs to 127. The static mix measures 28 µs with the
framework's static cache revalidating once per window (MoroJS 1.8.21).

## Record order with a request in the handshake flight

A TLS 1.3 server sends its session tickets right after the handshake. When a
client's first request arrives in the same read as its Finished, the engine
now writes those ticket records before it dispatches the request, so a reply
written synchronously from the handler follows them on the wire. The memory
BIOs kept that order by accident, through their shared queue; the view BIOs
keep it on purpose. The TLS conformance, hardening and reload suites run
against real clients (Node's `tls`, curl, `openssl s_client`) and pass as
before.
