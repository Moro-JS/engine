# @morojs/engine 1.2.1

One change, for applications that load the engine with `import`: the
process's resident memory is 5 to 18 MB lower, once per process, on the
Node.js versions listed below. Nothing else changes: no export, option or
capability flag is added, removed or renamed, and nothing on the wire
changes. Applications that `require()` the engine were never affected and
see no difference.

## Memory: `import '@morojs/engine'` no longer costs more than `require()`

The package's ESM entry (`index.mjs`) used to bring in the loader with
`import engine from './index.js'`. The loader is CommonJS, and for an ESM
import of a CommonJS file Node.js first runs a JavaScript lexer over the
whole source to guess its export names. The 1.2.0 loader is long enough
(30 KB, from 19 KB in 1.1.21) for V8 to start optimising that lexer while
it runs, and the memory the optimising compiler takes for that stays in the
process afterwards. The ESM entry does not use what the lexer finds: it
names every export itself.

`index.mjs` now takes the loader through `require()` (`createRequire`). It
is the same module instance a CommonJS consumer gets, so the default export
and every named export are what they were.

Resident memory after `import engine from '@morojs/engine'`, and of an idle
server that does nothing else, before and after (lowest and highest of
several processes, MB):

| Platform, Node.js | import, 1.2.0 | import, 1.2.1 | idle server, 1.2.0 | idle server, 1.2.1 |
| --- | --- | --- | --- | --- |
| macOS arm64, 24.11.0 | 62-63 | 44 | 65-66 | 47 |
| Linux arm64 glibc, 24.11.0 | 50-62 | 48 | 64-71 | 56 |
| Linux arm64 glibc, 22.23.5 | 53 | 42 | 59-60 | 48 |
| Linux arm64 musl, 24.11.0 | 54-60 | 53 | 67 | 60-62 |
| Linux arm64 musl, 22.23.5 | 54 | 47-48 | 60-62 | 53 |
| Linux arm64 musl, 20.20.2 | 46-48 | 42 | 52 | 47-49 |

On Node.js 24.22.3 and 26.13.1 there was nothing to save: those versions do
not optimise the lexer for this file, and `import` already cost what
`require()` does (45 MB and 51 MB idle on glibc with 24.22.3, before and
after).

It is a fixed amount per process, not per connection or per request, and it
does not grow: a cluster of eight workers on an affected Node.js version
holds eight times that less.

## Bundlers

Mark `@morojs/engine` as external, as for any package with a native binary;
that works as before. For builds that bundle it into the output anyway:

- esbuild to CommonJS keeps working, and esbuild to ESM now works too (it
  failed at start-up in 1.2.0 with "Dynamic require of ... is not
  supported"). In both, the engine's loader is no longer copied into the
  bundle: it is required at run time from the installed package, where the
  platform binary has to be anyway.
- webpack 5 bundling the engine inline did not work in 1.2.0 and does not
  now ("Cannot find module"); externalise it.
