# @morojs/engine 1.2.0

A security, correctness and performance release. It fixes a TLS session
resumption path that skipped the client-certificate check, two HTTP/2 ways
for one client to make the server hold or run without bound, a
`wsBackpressureLimit` that did not bound anything, several uses of freed
memory and several process aborts (in batched dispatch, `wsSend()`, the
libuv transport, HTTP/2 and the V8 boundary), and brings HTTP/1.1,
WebSocket and HTTP/2 framing in line with the RFCs. It adds `ssl.crl` and
`ssl.maxVersion`, makes the TLS options the engine used to ignore take
effect, loads on glibc 2.28 and later, builds musl and Windows binaries with
profile-guided optimisation, and runs fewer engine instructions per request
than 1.1.21 on Linux arm64: 20 to 24% for plain, pipelined and HTTPS
requests and for HTTP/2, 40 to 45% for WebSocket echo, 48% for pipelined
HTTPS, 12 to 15% for engine-answered routes, 2% for a new TLS connection (see
"Performance"). A number of behaviours a working
application or a correct client could notice change; they are listed, with
who notices and what to do, under "Changes you may notice".

Who should update, most severe first:

- High. Anyone who shares `ssl.ticketKeys` between servers with different
  client-certificate settings (for example a public listener and a
  `requestCert` listener), or who calls `updateSsl()` with a different client
  CA: a client could resume a session issued under the other policy and be
  served without presenting a certificate. 1.1.21; older releases were not
  checked (see "TLS").
- High. Anyone who runs with `http2` on, on 1.1.19 or later: one client could
  start an unbounded number of concurrently running handlers on one
  connection without being sent a `GOAWAY` (the rapid-reset budget was not
  charged for resets the server raises itself); one that does not read its
  socket was answered without bound (20,000 requests handled, +1,365 MiB of
  memory from about 900 KB of input); and one that closes its flow-control
  windows kept responses held indefinitely (+263 MiB for 256 responses of
  1 MiB; see "HTTP/2").
- High. Anyone who sends WebSocket messages from `onWsMessage` to peers they
  do not control, on 1.1.16 to 1.1.21: `wsBackpressureLimit` did not bound
  what was queued for a peer that does not read (63 kB received could hold
  150 MiB for up to `responseTimeoutMs`).
- High. Use of freed memory, reachable from the network or from application
  code: an engine-answered route (`setStaticRoute`, `setParamRoute`,
  `clear*`) answered from a stale table when the application changed routes
  while a request head was half received (reproduced on 1.1.13 and on this
  release's tree before the fix; by reading, since 1.1.10; MoroJS does this);
  the batch buffers after `getBatchBuffers()`'s ArrayBuffers are transferred;
  and, on Linux, a freed connection read at shutdown (epoll).
- High. Process aborts: the pipelined WebSocket handshake with batch dispatch
  and `setWsAutoUpgrade()` (1.1.15 to 1.1.21); `wsSend()` on Linux with Node
  23 or later (1.1.16 to 1.1.21); `close()` inside `onWsClose` on the libuv
  transport (macOS, Windows, Linux with `MORO_ENGINE_TRANSPORT=uv`; since
  1.0.0); and, on HTTP/2, a response call whose arguments run JavaScript that
  answers the same request (since 1.1.19).
- Medium. Anyone whose server is reachable by clients they do not control: an
  HTTP/1.1 connection could make the server buffer input without bound
  (`maxPendingBytes` was counted per response; 262 MiB sent, +717 MiB of
  memory) and could have pipelined requests answered into memory while
  reading nothing; replies to a WebSocket peer that had reset the connection
  were held until the failed write was reported (+603 MiB from four
  connections on libuv and io_uring, 1.1.21). With `http2` on (1.1.19 or
  later), a flood of 1-byte connection WINDOW_UPDATEs, uncharged, kept a
  server thread busy while responses waited on flow control, and one
  connection could reserve about 16 times the request-body bytes it sent.
- Medium. TLS on the OpenSSL binary (every release up to 1.1.19; the
  alternative binary since): a peer sending KeyUpdate or renegotiation
  requests without reading the replies made the server queue them without
  bound. Anyone who relied on `ssl.crl`, `ssl.maxVersion`, `requestCert: 1`
  or node's `--tls-min-v1.3`, `--tls-max-v1.2`, `--tls-cipher-list` having an
  effect: they had none on the engine (see "TLS").
- Medium. Linux servers at their descriptor limit (the loop spun at 78 to 97%
  of a core, io_uring since 1.1.6, epoll since 1.1.10), and anyone calling
  `listen()` twice or after `stopListening()` on epoll or io_uring.
- Anyone on Debian 11, Ubuntu 20.04 or a RHEL 8 family distribution: the
  Linux glibc binaries of 1.1.13 to 1.1.21 did not load there; these ones do
  (see "Release binaries and build").
- Anyone who consumes this project's releases: the scheduled BoringSSL roll
  could have published whatever was on `main` to `latest` (since 1.1.20; its
  release path had not run yet).

Additive for existing callers: the capability flags `wsAutoUpgradeBatch`,
`idleSparesDrainingResponse` and `tlsCrl`; the serve options `ssl.crl` and
`ssl.maxVersion`; the `probe().binary` field; two build flags (`--pgo-library`,
`--pgo-library-profile=F`) and one variable (`TRAINING_NODES`) in the build
tools. No export is removed or renamed and no existing serve option changes
its name. Some existing options and calls change meaning or strictness:
`wsBackpressureLimit` no longer closes a socket for the size of a single
message; `responseTimeoutMs` now also covers HTTP/2 responses held by flow
control; `serve()` throws for a TLS policy option of the wrong type;
`listen()` throws `EINVAL` where it used to open a second listener. All of
them, and every other change on the wire, are listed next.

## Changes you may notice

Each item says who notices and what to do. Most concern clients and
applications at the edges of the protocols; the items that a working
application or a correct client can notice say who.

Connections and limits:

- **A client with more than `maxPendingBytes` of requests outstanding in
  total is disconnected** (HTTP/1.1 and HTTP/2; the bound used to be counted
  per response). Who: a client that pipelines more than 10 MiB + 64 KiB
  while reading nothing. Do: nothing; raise `maxPendingBytes` if you mean to
  accept it. On HTTP/2 the bound is `maxPendingBytes` plus one connection
  window.
- **An HTTP/2 download that a client holds closed through flow control for
  longer than `responseTimeoutMs` (300 s by default) is disconnected.** Who:
  an HTTP/2 client that pauses a download that long. Do: raise
  `responseTimeoutMs` or set it to 0.
- **`idleTimeoutMs` no longer cuts a response still being delivered** (it is
  governed by `responseTimeoutMs`). Who: servers that relied on the idle
  timeout to cut slow downloads. Do: set `responseTimeoutMs`.
- **An HTTP/2 connection whose peer does not read stops processing frames at
  the write high-water mark**; a slow reader's later frames (new requests,
  cancels) are acted on after its queue drains.
- **Uploads on one HTTP/2 connection that together exceed what it buffers**
  have the newest refused with `REFUSED_STREAM` (safe to retry) instead of
  stalling the connection. Who: clients running several multi-megabyte
  uploads at once.
- **A cleartext HTTP/2 connection that sends part of the preface and stops**
  is answered 408 after `requestTimeoutMs`.
- **Linux, io_uring: a peer arriving at the descriptor limit is turned away
  within a sweep (1 s at most)**, not at once.
- **`listen()` throws `EINVAL`** on a server that is listening, has stopped
  listening or is closing, on every transport. Who: code that called it
  twice; on io_uring the second call used to appear to work until `close()`.
  Do: call it once.
- **A request that arrives behind a `Connection: close` response is dropped**
  (batch dispatch). Who: a client that sends another request after saying
  `Connection: close`. Do: open a new connection.
- **After 400, 408, 413, 414, 431 and 505 the connection reads nothing
  more.**

Requests refused that were accepted before (400 unless stated):

- **HTTP/1.1 chunked framing:** a bare LF at the end of a chunk-size line,
  the last chunk or a trailer line; whitespace before a chunk size; a
  control byte in a chunk extension; a malformed trailer line. Who: hand
  written clients; none of the common HTTP clients sends these.
- **A `Host` value that is not a host** (HTTP/1.1, and `:authority` / `host`
  on HTTP/2): whitespace, `/ ? # @ \`, two hosts in one value, a comma
  outside the brackets of an IP literal, an IPv6 address without brackets,
  non-ASCII bytes. The comma case is a change from before; it is the
  shape of two `Host` fields merged by an intermediary. Do: send the `xn--`
  form of an internationalised name.
- **HTTP/2 requests with a control byte (other than HTAB) or DEL in a field
  value, a repeated `host` or `:authority`, or a `Host` or `:authority` with
  a path, userinfo or space** are refused, as on HTTP/1.1. Who: unusual
  clients only.
- **HTTP/2: when `Host` and `:authority` differ, `:authority` is what the
  application sees as `Host`** (RFC 9113 section 8.3.1; `Host` used to win).
  Who: clients that send different values, and an
  application that keys on the old behaviour.
- **HTTP/2: an `http` or `https` request with neither `:authority` nor
  `host`, or with an empty one, has its stream reset**
  (`RST_STREAM(PROTOCOL_ERROR)`), as HTTP/1.1 answers 400 without `Host`
  (RFC 9110 section 7.2 requires a client to send one). An empty
  `:authority` used to let the client's `host` field stand in its place. Who:
  only an HTTP/2 client that sends no authority or an empty one. Do: send
  `:authority` or `host`.
- **WebSocket handshakes:** a `POST`, `PUT`, `DELETE`, `OPTIONS` or `HEAD`
  with the upgrade headers, an HTTP/1.0 request, a repeated
  `Sec-WebSocket-Key` or `Sec-WebSocket-Version` are ordinary requests now
  (`upgradeToWebSocket()` returns `-1`); an unsupported version is answered
  426 by an engine-side upgrade.
- **permessage-deflate offers** with a repeated parameter, a value on a
  `*_no_context_takeover`, or window bits with a leading zero are declined
  (the connection opens uncompressed).
- **An over-long HPACK integer is rejected**; **empty DATA frames on a closed
  stream** now count against the control-frame budget.

Responses and application calls:

- **A stack trace taken inside a request handler has one more frame**, the
  loader's, below the handler's own (see "Binding to JavaScript"). Who: code
  or tooling that counts frames or matches the bottom of a handler's stack.
  Do: nothing; `MORO_ENGINE_DISPATCH=scope` restores the previous entry.
- **`respond()` or `respondPrepared()` after `writeHead()` or `write()`:**
  on HTTP/1.1 the response ends where it is and the connection is closed (it
  used to put a second status line on the wire); on HTTP/2 the body is
  finished through `end` (it used to send a second HEADERS frame). Who: an
  error path that responds after streaming started. Do: end the response, or
  check `headersSent`.
- **A response call whose arguments run JavaScript that answers the same
  request** acts once.
- **`wsSend()`** returns `false` for a payload it cannot send, for every send
  made after a socket's shed is pending, and inside `onWsClose`; on libuv and
  io_uring a send in the turn a peer reset may still return `true`.
  **`wsClose(code, reason)`** sends legal codes as given, 1011 for others and
  cuts the reason to 123 bytes.
- **A slow but reading WebSocket client that is shed** no longer receives the
  sends made between the shed and its Close(1013).
- **`onWsClose(1006)` arrives after `wsSend()` returns** on epoll (and on the
  other transports as before); `write()` to an HTTP connection reset under a
  queued response answers `false` on epoll.
- **Data received from a peer before it reset is delivered on epoll** (and
  io_uring), as on libuv on Linux and macOS: an application may see
  messages it never saw before. (Not on Windows, where a reset discards
  what the connection had received and not yet read.)
- **A compressed message that is not a deflate stream closes with 1007**,
  not 1009. **A Close the server starts lingers up to two seconds** on
  plaintext, so the peer receives it.
- **A streamed response without a length to an HTTP/1.0 client** is sent
  unchunked with `Connection: close`; no `100 Continue` for HTTP/1.0; 204 and
  1xx carry no `Content-Length`; 205 goes out with `Content-Length: 0`; every
  registered status has its reason phrase (`statusText` is no longer `OK`
  for them).
- **Wire bytes**: small replies answered in one batch over TLS share TLS
  records; large bodies and chunks are written in other pieces (same bytes in
  the stream). Nothing a client parses changes.

TLS and loading:

- **A TLS session is resumed only by a server with the same policy**; others
  get a full handshake. Who: deployments sharing `ssl.ticketKeys` between
  servers of different policy, and the first connections after an
  `updateSsl()` that changed the CA or cipher list.
- **`serve()` throws for a TLS policy option of the wrong type**
  (`requestCert: 1`, `minVersion: 1.3`, `ciphers: [...]`). Who: an
  application passing one; it was silently read as unset. Do: fix the type.
- **`node --tls-min-v1.3`, `--tls-max-v1.2` and `--tls-cipher-list` are the
  defaults of an engine TLS server** (the application's own values win), and
  OpenSSL options in node's configuration file select the OpenSSL binary.
  Who: processes started with those flags get the stricter TLS they asked
  for. `ssl.crl` and `ssl.maxVersion`, if you already passed them, are now
  enforced: a revoked client certificate is refused.
- **A peer that floods KeyUpdate or renegotiation without reading is closed**
  past 256 KiB of unread replies.
- **A platform package of another release, or one outside the
  installation's `node_modules`, is not loaded** (`probe().error` says so).
  Who: installs that relied on a binary in an ancestor directory,
  `NODE_PATH` or `~/.node_modules`. Do: install the package in the
  application, or set `MORO_ENGINE_BINARY`.
- **An installed copy no longer looks in `node_modules/build`.**

Release tooling:

- `tools/release.mjs` refuses a version that is not above the current one,
  and refuses `patch|minor|major` while at a release candidate.

## Batched dispatch

- **A process abort that could occur with pipelined WebSocket handshakes
  when batch dispatch (`onRequestBatch`) and engine-side upgrades
  (`setWsAutoUpgrade`) were both enabled is fixed.** Affected: 1.1.15 to
  1.1.21. A server that uses only one of the two, or neither, was not
  affected. In the same situation a handshake could also be delivered twice,
  as a WebSocket and as a request to the HTTP handler; that is fixed with
  it. For a batch loop the visible change is that `control[0]` may now read
  `count` or more before every slot has been dispatched, which the
  documented loop already returns on.
- **`capabilities.wsAutoUpgradeBatch`** (new) is `true` on an engine with
  that fix. An engine that reports `wsAutoUpgrade` and `batchDispatch`
  without it must not be given both.
- **A response sent from a microtask or `process.nextTick` of the batch call
  no longer strands the requests staged behind it.** JS had already left its
  loop, so nobody was reading the control cell when the next slot was
  activated; the slot is now delivered in a call of its own. The HTTP/2
  batch had the same gap, with the slot behind such a response skipped.
- **A connection closed from inside the loop over its own batch ends the
  loop.** A handler that closed the server (or tripped
  `responseBackpressureLimit`) left the remaining slots of its batch to be
  dispatched: handlers ran for requests that no longer existed, after their
  `onAborted` had been delivered. On HTTP/2 the requests the loop had not
  reached were also reported aborted without ever having been handed over.
  Now none of them reaches a handler, and none is reported, except that the
  one slot the loop was about to take may still get its `onAborted`.
- **The batch buffers stay valid when JavaScript transfers them away.**
  `descriptors.buffer.transfer()` of the ArrayBuffers `getBatchBuffers()`
  returns, followed by a collection, left every later batch writing
  descriptors into freed memory (reproduced under AddressSanitizer). The
  server now holds their backing stores, and a later `getBatchBuffers()`
  returns working buffers over new storage (it used to abort the process on
  a V8 check); a batch in progress carries on.
- **A pipelined request that waited while the 32-bit request id counter came
  round no longer takes over an id given out in the meantime.** A staged
  request gets its id when staged and is registered when activated; after a
  lap of the counter the same number could belong to a live request, and that
  request's response was written to the staged request's connection. It is
  re-activated under a new id, and a JavaScript loop holding the old
  descriptor is told its batch is over. Needs batch dispatch, a request kept
  staged while 2^32 requests go by on the thread. An id an application keeps
  for more than 2^32 requests cannot be protected at 32 bits.

## Binding to JavaScript

- **Request callbacks are entered through `node::MakeCallback`.** `onRequest`,
  `onRequestBatch`, `onAborted` and `onWritable` are wrapped once at
  `serve()` in small try/catch functions in the loader, so the engine no
  longer builds a callback scope and a native exception catcher around every
  dispatch. Counted over the whole process (node and compiled JavaScript
  included): 3.1% fewer instructions for a plain request, 3.7% for a
  prepared response, 2.5% for a JSON POST, 3.6 to 4.4% where batch dispatch
  is off; pipelined requests, static routes and WebSocket are unchanged.
  What a callback can observe is the same as before, checked by running one
  server under both entries and comparing everything it sees (`this`, async
  hooks, `AsyncLocalStorage`, a throwing handler, a throw from a nextTick
  callback or a microtask reaching `uncaughtException`, a rejected promise,
  worker threads) on Node 20, 22, 24 and 26. One thing differs: a stack
  trace taken in a handler has one loader frame below the handler's own.
  `MORO_ENGINE_DISPATCH=scope` restores the previous entry. WebSocket
  callbacks keep the previous entry (the new one cost 6% where each read
  carries one message).
- **With `MORO_ENGINE_NOTIFY=sync` (a diagnostic mode), an aborted request
  is released before `onAborted` runs**, on HTTP/1.1 and HTTP/2. A streaming
  handler waiting on backpressure when its client went away, or when its
  HTTP/2 stream was reset, saw `isAborted()` false inside `onAborted` and
  waited for an `onWritable` that could not come. In the same mode: ending
  an HTTP/2 response from `onWritable`, or ending other requests from
  `onAborted`, no longer uses released state (a stream read after it was
  freed; a request slot that then served two requests), and an HTTP/1.1
  `write()` without `writeHead()` no longer reads its body after the
  implicit head closed the connection. The default mode was not affected.
- **A callback that throws from deep in the stack is always caught and
  logged** (for example `onAborted` run by a `close()` called near the stack
  limit: the throw escaped into the caller of `close()`, unlogged). A thrown
  value that cannot be turned into a string (a Symbol, a throwing
  `toString`) is logged instead of dropped, under both entries.
- **A response call whose arguments run JavaScript that answers the same
  request acts on it once.** `respond`, `writeHead`, `respondPrepared`,
  `respondPreparedEmpty`, `writeHeadPrepared` and `getHeader` resolved the
  request id before reading arguments that can run JavaScript (`valueOf`,
  `toString`, a getter). If that JavaScript answered the request, the outer
  call acted on it again: on HTTP/1.1 it wrote a second response onto the
  keep-alive connection, which the client read as the answer to its next
  request; on HTTP/2 the request's connection object was already back on the
  free list and the process aborted. The id is now resolved after the
  arguments are read. Application code only; needs a getter or coercion that
  re-enters. HTTP/2 exists from 1.1.19.
- **`serve()` with a getter that throws creates no server** (it threw and
  still built one nobody could close).
- **A handler cut short by `worker.terminate()` is no longer logged as
  having thrown.**
- **The notification mode, batch dispatch and fast-call switches are read
  from the environment once per process**, not on every thread's load, so a
  later worker cannot flip them under a thread with fast calls installed.
- **macOS: a worker thread can load the engine after the last thread that
  held it has ended.** The second worker used to load the other TLS binary
  and the third failed with "Module did not self-register". Linux glibc was
  not affected.

## HTTP/1.1

Memory and timeouts:

- **Pipelined requests are no longer answered into memory for a peer that is
  not reading.** A response a handler gives before it returns was counted as
  delivered once it was framed, and the next pipelined request was taken at
  once, so the responses queued for one connection were bounded only by how
  many requests it sent. Now, once `writeHighWaterMark` (256 KiB) of response
  bytes are waiting on the peer, no further request is parsed, staged or
  handed to a handler on that connection until they drain; what the client
  sends meanwhile is buffered up to `maxPendingBytes`, as it always was
  behind a handler that answers later. Per connection the engine holds the
  high-water mark plus the one response that crossed it. `docs/THREAT_MODEL.md`
  already described this bound; it now holds for synchronous handlers too.
  Who notices: nobody who reads responses as they arrive. A client that
  pipelines more than `maxPendingBytes` (default 10 MiB + 64 KiB) of requests
  while reading nothing is disconnected, where it used to be served into the
  server's memory. In a batch loop `control[0]` may read `count` or more
  before every slot has been dispatched, which the documented loop already
  returns on; the remaining slots arrive in a later batch.
- **The framing of a chunked request body no longer accumulates.** Chunk-size
  lines and chunk extensions were kept in the parser's buffer until the
  request completed, and `maxBodySize` does not count them, so the memory a
  request in progress could hold was not bounded by it. They are now dropped
  as the chunks are consumed.
- **`idleTimeoutMs` no longer cuts a response that is still being
  delivered.** A large response given before the handler returned, to a
  client reading it slowly, was closed at the idle timeout, because the
  connection counted as idle from the moment the response was framed. A
  connection with response bytes queued is now governed by
  `responseTimeoutMs` (which also closes a peer that stops reading), as it
  already was for a handler that answers later. With `responseTimeoutMs: 0`
  the idle timeout still applies. **`capabilities.idleSparesDrainingResponse`**
  (new) is `true` on an engine with this behaviour; on an engine without it,
  set `idleTimeoutMs` above your longest download or leave it off.
- **A rejected request stays rejected.** After a 400, 408, 413, 414, 431 or
  505 the connection reads nothing further, from the moment the error
  response is written or queued; it used to go on parsing until that
  response had been flushed, or until a handler still running ahead of the
  rejected request had answered. A connection now gets one error response,
  and the handler never runs for a request the client was told is refused.
- **Nothing is answered behind a `Connection: close` response.** With batch
  dispatch, a request that arrived while the last response of a connection
  (`Connection: close`, HTTP/1.0) was still being written was parsed and
  answered after it. It is now dropped, as a request that arrives once that
  response is out always was (the lingering close of 1.1.6). Who notices: a
  client that says `Connection: close` and then sends another request on
  the same connection; it has to open a new one, as the header promised.
- **A chunk that would take a chunked body over `maxBodySize` is refused at
  its size line** (413). It used to be buffered whole first, on top of the
  body collected so far, so a request in progress could hold up to twice the
  limit. Same status as before, sent sooner.
- **`maxPendingBytes` bounds all input received and not yet dispatched on a
  connection.** It was counted per response: a client that sent just under
  the limit after each response made the server buffer input without bound
  (262 MiB sent, +717 MiB of memory, connection still open; reproduced on
  1.1.13). Now the limit counts what is waiting plus what the parser has not
  consumed, and the connection is closed past it. Who notices: a client with
  more than `maxPendingBytes` outstanding across several responses.
- **A request to an engine-answered route could be answered from freed
  memory.** The route hook stores pointers into the route tables at the
  request line; when the head arrived in more than one read and the
  application changed its static or parameter routes (`setStaticRoute`,
  `setParamRoute`, `clear*`, which MoroJS does when a route is registered at
  run time) before the head completed, the answer was framed from the old
  table: another route's reply, a 500 without a content type, or a crash.
  The peer sends only the request line and waits (up to `requestTimeoutMs`,
  repeatably). The route is now matched again when the head completes; if it
  is gone the request is answered 500 and the connection closed, as for an
  emptied table. Reproduced on 1.1.13 and on this release's tree before the
  fix; by reading, since 1.1.10; not tested over TLS separately.
- **`respond()` or `respondPrepared()` after `writeHead()` or `write()` no
  longer writes a second status line** into the response in progress. The
  response ends where it is and the connection is closed, so the client sees
  a cut-short response, not a desynchronised keep-alive connection (the
  declared length 20 with 5 bytes sent was followed by a whole second
  response). MoroJS guards on `headersSent` and was not affected.
- **A request body's buffer is reserved in full only once a sixteenth of its
  declared length has arrived** (at once up to 64 KiB). A head declaring a
  large body no longer sets that memory aside (8 MiB for one byte before).
  HTTP/2 and WebSocket messages do the same.

Requests (the first three are a 400 where there was a 200, for requests no
browser, curl, or HTTP client of Node, Go, Java, .NET or Python sends; the
rest change which requests are refused only at the limits):

- **Chunked framing requires CRLF** (RFC 9112 §7.1). A bare LF was accepted
  at the end of a chunk-size line, of the last chunk and of trailer lines.
  It is still accepted where §2.2 allows it, in the request line and the
  header fields. Whitespace before a chunk size (` 3`) is rejected; after it
  (`3 `, `3 ;ext`) it is still tolerated. A control byte in a chunk
  extension is rejected.
- **Trailer lines are checked as header lines are** (a token name, a colon,
  a value without control bytes) instead of being skipped unread. They are
  still dropped, never merged into the request's headers.
- **The `Host` value must be a host** (RFC 9112 §3.2, RFC 9110 §7.2): a name
  or IPv4 address, or an IPv6 address in brackets, optionally followed by a
  colon and a port of digits. Accepted as before: underscores (`my_service`),
  a trailing dot, upper case, an empty port (`localhost:`), an empty value.
  Now 400: a value with whitespace, `/`, `?`, `#`, `@` or `\`, two hosts in
  one value, a comma (still accepted inside an IP-literal's brackets; a change from before:
  no DNS name has one, and it is the shape of two `Host` fields merged
  by an intermediary), a second colon outside brackets (an IPv6 address without its
  brackets), and non-ASCII bytes (an internationalised name that was not
  converted to its `xn--` form).
- **A chunk-size line is limited to 16 KiB, however it arrives.** The limit
  used to be 1 KiB when the line was split across reads and none when it
  arrived in one, so the same request could be accepted or refused depending
  on how TCP delivered it. Extensions between 1 KiB and 16 KiB are now always
  accepted; longer ones are always refused.
- **A chunked request is no longer answered 431 because of the request
  pipelined behind it.** The trailer limit (`maxHeadSize`) counted everything
  in the buffer after the last chunk; it now counts the trailer section.
- **431 or 400 for a head that is over `maxHeadSize` and also malformed no
  longer depends on how it arrived.** A line is answered 431 once the head up
  to and including it is over the limit, malformed or not, and 400 (or 414,
  505) if it is malformed while the head is still within it. Only requests that
  were already refused are affected, and only in which of the two statuses
  they get: a short malformed request line used to be answered 431 when the
  same read held more than `maxHeadSize` bytes behind it (now 400), and a
  malformed header line that crossed the limit was answered 400 when it
  arrived in one read (now 431, as it always was when it arrived in pieces).

HTTP/1.0 clients (`ab`, `curl -0`, nginx with its default
`proxy_http_version 1.0`, some health checkers):

- **A streamed response without a declared length is not chunked for an
  HTTP/1.0 client**, which cannot read chunked framing and would take the
  chunk sizes for content. The body is sent as it is, with
  `Connection: close`, and the end of the connection ends it (RFC 9112
  §6.1, §6.3) - also when the client asked for keep-alive, since nothing
  else can end such a body. `respond()` and streamed responses with a
  `content-length` are unchanged, keep-alive included. A proxy that decoded
  the chunked response anyway (nginx does) sees the same body as before.
- **`100 Continue` is not sent to an HTTP/1.0 client** (RFC 9110 §10.1.1),
  and an HTTP/1.0 request that carries `Transfer-Encoding` is answered and
  the connection then closed (RFC 9112 §6.1).

Responses:

- **No `Content-Length` on a 204 or 1xx response** (RFC 9110 §8.6): one
  supplied by the handler was sent. It is still sent where it is meaningful,
  on a 304 and on a HEAD response. **A 205 response has no content**
  (§15.3.6): it goes out with `Content-Length: 0`, whatever body the handler
  gave it. Both also on HTTP/2.
- **Reason phrases**: every registered status code has its own. Codes outside
  the 23 the engine knew were sent as `429 OK`, `502 OK`, and so on. Clients
  must not act on the phrase, but logs, `curl -i` and `fetch()`'s
  `statusText` show it; code that compares `statusText` to `"OK"` for one of
  those statuses will see the real phrase. Unregistered codes still say `OK`.

Tests and fuzzing:

- The parser paths every first read takes (the in-place scans behind the
  route hook) had no unit or fuzz coverage; `test/http-parser-unit.cpp` now
  compares them with the buffered path at every split point, and
  `test/fuzz/fuzz_http_diff.cc` (`sh test/fuzz/run.sh httpdiff`, in the
  per-commit smoke and the nightly campaign) does the same on arbitrary
  input: any difference in status, error code, request or leftover bytes
  between the paths, or between one read and several, fails the run.
- The sanitizer build (`node tools/build.mjs --sanitize`, never shipped) is
  compiled with fault points: failures no peer can provoke, switched on by a
  test (`probe().testFaults` is `true` on such a build and absent on any
  other). The first is a TLS session that refuses to encrypt; the test that
  needs it is skipped, with the reason, on every other build. CI's
  sanitizer job now runs the suites on the epoll transport too - it ran
  them on libuv and io_uring only, not on the Linux default.
- `test/fast-api.test.mjs` skips its three fast-path tests, with the reason,
  where V8 runs without its optimising compiler: an x86-64 `node` under
  emulation (a `linux/amd64` container on Apple silicon, where V8 starts
  with TurboFan off), `--no-opt`, `--jitless`. No call is optimised there,
  so none can take a fast path, and the tests failed for a reason that was
  V8's. Where V8 optimises they run as before.

## HTTP/2

HTTP/2 is in this tree from 1.1.19; where a version is given, it is that
release or later.

- **The rapid-reset budget could be bypassed with resets the server raises
  itself** (CVE-2023-44487's defence sidestepped). A peer's `RST_STREAM` costs
  4 budget units, but `DATA` after `END_STREAM`, a `WINDOW_UPDATE` of 0 or
  one that takes the window past 2^31-1, a self-dependent `PRIORITY` and
  `HEADERS` after `END_STREAM` made the server reset the stream at no cost
  while the handler kept running: 8,000 handlers running at once on one
  connection with no `GOAWAY`, against 600 and a `GOAWAY` for client resets.
  Affected: 1.1.19 and later, any client, `http2` on, async handlers. Now a
  reset of a stream whose request a handler holds costs the same 4 units (1
  otherwise) and the connection gets `GOAWAY(ENHANCE_YOUR_CALM)` at the same
  point (600 handlers).
- **A client that does not read its socket is no longer answered without
  bound.** Each response's stream closed as soon as it was framed, so
  `maxConcurrentStreams` never applied, and HTTP/2 input was not held at the
  write high-water mark as HTTP/1.1 input is: 20,000 requests handled and
  +1,365 MiB of memory from about 900 KB of input (HTTP/1.1: 28 handled,
  +3 MiB; now 32 handled, +6 MiB). Now the session stops at the current
  frame once `writeHighWaterMark` of response bytes wait; input is kept up
  to `maxPendingBytes` plus one connection window (then the connection is
  closed) and processing resumes as the queue drains. Present since 1.1.19
  by reading; reproduced on this release's tree before the fix.
- **`responseTimeoutMs` now also covers responses held behind closed
  flow-control windows.** A peer that sent `SETTINGS_INITIAL_WINDOW_SIZE=0`,
  opened 256 streams and pinged kept 256 responses of 1 MiB held (+263 MiB)
  with the connection open indefinitely, because both limits looked only at
  the socket queue. The sweep now closes an HTTP/2 connection that has held
  response bytes and sent none of them for `responseTimeoutMs`; a PING
  acknowledgement is not progress. `responseBackpressureLimit` does not count
  these bytes (a normal client with the default 64 KiB window would trip it
  on any larger response); the documentation says so.
  Behaviour change: see "Changes you may notice".
- **Parallel uploads from a correct client no longer wedge the connection.**
  Past the buffering bound the connection window was withheld; once spent, no
  unfinished request could complete and it never reopened (six 9 MiB uploads:
  none handled after 5 s, until the idle timeout). The newest unfinished
  streams are now refused with `REFUSED_STREAM` when the bound is exceeded
  with the window spent, and the rest complete. A reset or a 413 on a
  buffered upload also reopens the window now.
- **A SETTINGS frame that repeats `SETTINGS_INITIAL_WINDOW_SIZE` updates the
  open streams once, not once per entry** (1,900 frames with 256 open
  streams: 826 ms of CPU, now 6.4 ms; the last value wins and an overflow
  partway through is still `FLOW_CONTROL_ERROR`).
- **Requests HTTP/1.1 refuses are refused**: control bytes other than HTAB
  and DEL in field values, two `host` lines, a `Host` or `:authority` with a
  path, userinfo or space (or a comma), a repeated `:authority`. When `Host`
  and `:authority` differ, `:authority` is delivered as `Host` (RFC 9113
  section 8.3.1); an `http` or `https` request with neither, or with an
  empty `:authority` or `host`, is refused (`RST_STREAM(PROTOCOL_ERROR)`).
- **An HPACK integer with a fifth continuation byte of 0x10 or more** wrapped
  modulo 2^32 and was accepted as a small value; it is rejected.
- **Empty DATA frames on a closed stream** were answered with a reset each
  and not charged; they cost the 1 unit the document states.
- **`respond()` after `writeHead()` finishes the response body** instead of
  sending a second HEADERS frame.
- **A cleartext connection that sends part of the preface and stops** is
  subject to `requestTimeoutMs` (it sat outside it; only the idle timeout
  applied). Request headers or a body that arrive slowly after the preface
  are still outside it, as documented.
- **Request bodies are reserved as they arrive**: a declared
  `content-length` above 64 KiB is reserved only once a sixteenth of it has
  arrived (256 streams each declaring 10 MiB and sending one byte: +8 MiB
  with the lazy reserve), and a body is no longer copied twice on arrival.
  The room reserved for declared bodies counts against the connection's
  buffer bound (`maxBuffered`): 48 streams on one connection could reserve
  about 16 times what they sent (+484 MiB of address space; now +49 MiB).
- **WINDOW_UPDATE frames beyond what a connection has earned draw on the
  control-frame budget.** A connection-level WINDOW_UPDATE was never charged
  and walked every stream waiting on flow control: a flood of 1-byte
  increments with 256 waiting streams cost the server 150 times the work of
  the same flood with none, and kept a thread busy. Each connection now has
  16 free updates plus 2 per stream and 1 per KiB of DATA sent, and a
  connection update visits only streams waiting on that window; the flood is
  closed with `GOAWAY` within milliseconds. A client that grants window as
  it reads stays well inside the allowance.
- **Separate `cookie` fields arrive as one**, joined with "; " (RFC 9113
  section 8.2.3), as on HTTP/1.1. A framework that folds repeated fields
  with ", " corrupted them.
- **No `Content-Length` on 204 or 1xx and `Content-Length: 0` on 205**, as on
  HTTP/1.1 (listed under "HTTP/1.1").
- The HTTP/2 fuzz target and unit suite run in CI; 24 seeds were added and the
  existing 29 renamed with the `.raw` suffix they needed to be tracked at all.
- h2spec is unchanged: 146/146 over TLS, 145/146 cleartext (the documented
  case), on epoll, io_uring and libuv.

## TLS

- **Session resumption no longer skips the client-certificate check.** The
  session-ID context was a constant, so a session issued under one policy
  was accepted by any server sharing `ssl.ticketKeys`, and by the same
  server after `updateSsl()`: a client with a session from a public server
  and no certificate was served by a `requestCert` server (both libraries,
  TLS 1.2 and 1.3). On the OpenSSL binary a TLS 1.2 session also kept a
  cipher that the other server's list, or the list after `updateSsl()`,
  excluded. The context is now a SHA-256 over the policy: `minVersion`,
  `ciphers`, `ciphersuites`, `requestCert` / `rejectUnauthorized`, the sorted
  fingerprints of the CA store and, with `ssl.crl`, the CRLs. A server with
  the same policy still resumes, and so does a certificate rotation. Present
  in 1.1.21; older releases were not checked. Who is affected: servers that
  share `ssl.ticketKeys` across different client-certificate policy, or call
  `updateSsl()` with a different client CA or cipher list.
- **A peer that sends KeyUpdate or renegotiation requests without reading
  the replies is closed once 256 KiB of replies wait on it.** OpenSSL
  answers each request with a record, the engine queued them without bound
  (7.7 MiB queued for 300,000 KeyUpdates, 8.9 MiB for renegotiation requests;
  memory grew 1:1 with the bytes sent and a slow drain defeated
  `responseTimeoutMs`). Affected the OpenSSL binary: every release up to
  1.1.19, and the alternative binary since. The BoringSSL binary closes at 32
  consecutive KeyUpdates and treats renegotiation as fatal; it was not
  affected. No measurable cost on the request path.
- **`ssl.crl` and `ssl.maxVersion` are supported** (`capabilities.tlsCrl`).
  Node's `crl` option was ignored, so a revoked client certificate was served
  (both libraries); `maxVersion` was ignored too. With any CRL given, the CRL
  of every CA in a client's chain must be among them.
- **A policy option of the wrong type throws from `serve()`**: `requestCert:
  1` asked nobody for a certificate and `minVersion: 1.3` kept the TLS 1.2
  floor, because wrong types were read as unset.
- **`node --tls-min-v1.3`, `--tls-max-v1.2` and `--tls-cipher-list` apply to
  the engine's TLS servers** at `serve()` and `updateSsl()` (the
  application's own values win); they bound node's own servers but not the
  engine's. **OpenSSL options in node's configuration file**
  (`--experimental-config-file`) are detected and select the OpenSSL binary;
  BoringSSL had been loaded with reason `default`.
- **With `requestCert` and `rejectUnauthorized: false`, a client whose
  certificate does not verify is no longer dropped when its handshake arrives
  in several segments** (OpenSSL binary: a stale error from the chain check
  was read as the handshake's failure).
- **On BoringSSL, one redundant error-queue check per TLS read and write is
  gone**; small replies answered in one batch share TLS records, and large
  chunks are encrypted from the application's bytes (see "Performance").
- The TLS fuzz harness covers client certificates, split flights, KeyUpdate
  and renegotiation (174,449 runs, no failure).

## WebSocket

- **A process abort in `wsSend()` on Linux is fixed.** Reproduced on every
  release from 1.1.16 to 1.1.21 with Node 24, and on 1.1.21 with Node 23, 25
  and 26 as well; always on the epoll transport, the Linux default since
  1.1.10. When the peer of a WebSocket had reset the connection and the
  application sent it a string before the event loop had read the reset - a
  broadcast reaching a client that has just gone - the send met the error
  itself, and the engine reported the close by calling `onWsClose` from
  inside `wsSend()`. The binding is reading the payload out of the V8 heap
  at that point and no JavaScript may run: V8 ended the process (`Check
  failed: AllowHeapAllocationInRelease::IsAllowed()`), on a plain connection
  and over TLS. Where there was no abort, the callback still ran inside the
  send: on Node 20 and 22 (which do not read the payload that way), with a
  `Buffer` payload on any Node, and on 1.1.10 to 1.1.15. Not affected: 1.1.9,
  whose Linux default was libuv; the libuv and io_uring transports; macOS.
  (Windows runs the libuv transport and was not tried.)
  The epoll transport now ends a connection whose write failed from the
  loop, later in the same turn, as the other two transports always have:
  `onWsClose(1006)` arrives once `wsSend()` has returned. One answer changes
  with it for HTTP on that transport: the first `write()` to a connection
  that was reset under a queued response used to answer `true` for a chunk
  that was already lost, and now answers `false`, as it does on the other
  two; `onAborted` is delivered as before.
- **A send that cannot be completed never reports the close from inside
  `wsSend()`, on any transport.** Two more places closed a WebSocket on the
  spot when a send failed: a TLS session that could not encrypt, and a
  transport that refused the write outright. Neither has been seen to
  happen - no peer can provoke the first, and libuv reports a failed write
  later - but each would have run `onWsClose` inside the send, with the
  same result as above. The close is now queued and delivered on a later
  loop turn, the way the shed of a slow consumer has been since 1.1.16.
  An HTTP connection in the same situation is closed at once, as before:
  nothing is called for it there.
- **`onWsClose` fires once** when the callback itself calls `wsClose()` on a
  socket whose peer went away (it fired again, with the second code). Inside
  the callback `wsSend()` now answers `false` on every close path, and the
  handshake accessors still answer.
- **The handshake** (RFC 6455 §4.2.1): only a `GET` over HTTP/1.1 is
  upgraded. A `POST`, `PUT`, `DELETE`, `OPTIONS` or `HEAD` carrying the
  upgrade headers, and an HTTP/1.0 request, used to be switched to the
  WebSocket protocol; so did a request with two `Sec-WebSocket-Key` lines
  (the last one won) or two `Sec-WebSocket-Version` lines. Each is now an
  ordinary request: `upgradeToWebSocket()` returns `-1`, and with
  `setWsAutoUpgrade` it reaches `onRequest`.
- **An unsupported `Sec-WebSocket-Version`** on an otherwise valid handshake
  is answered by an engine-side upgrade with `426 Upgrade Required`,
  `Upgrade: websocket` and `Sec-WebSocket-Version: 13` (§4.2.2, §4.4); it
  used to reach `onRequest` as a plain request. With `upgradeToWebSocket()`
  the application still answers, as before.
- **`wsClose(code, reason)` always sends a legal Close frame.** A reason over
  123 bytes went out as a control frame longer than §5.5 allows, and any
  number was sent as the status code, 70000 as 4464. Now: codes that may
  appear on the wire (1000-1003, 1007-1014, 3000-4999) go out as given; 1005
  sends a Close without a status, which is what it means; any other value is
  sent as 1011; the reason is cut to 123 bytes at a UTF-8 character boundary.
  `onWsClose` reports the code as it was passed.
- **`wsSend()` returns `false` for a payload it cannot send** (a number, an
  object, `undefined`). It returned `true` and sent nothing.
- **The Close frame of a close the server starts reaches a peer that is
  still sending.** After its Close the server closed the socket at once; a
  peer in the middle of an upload was answered with a TCP reset that
  discarded the Close before it was read (measured: a 4 MiB message against
  a 1 MiB `wsMaxMessageSize` saw its 1009 in 6 of 30 attempts; now in all of
  them). The server now half-closes and reads, discarding, until the peer
  has closed its side (§7.1.1), for at most two seconds - the lingering close
  HTTP `Connection: close` responses have had since 1.1.6. Plaintext only: a
  TLS connection is closed after its `close_notify`, as before.
- **One large message no longer closes a socket whose peer is reading.**
  `wsBackpressureLimit` (default 1 MiB) is there to shed a consumer that is
  not keeping up, but any single `wsSend()` that left more than the limit
  unsent closed its socket with 1013 once the message was out - in practice
  every message over about 1.5 MiB on loopback, however fast its reader. A
  socket is now shed only by a send that finds bytes of an earlier send still
  waiting: one message sent to a socket with nothing queued goes out whole
  whatever its size and the socket stays open, and a peer that is not
  draining is shed by the next send, as before. A peer that stops reading
  with one such message in flight is closed by `responseTimeoutMs`. (Not on
  Windows, where Winsock takes the first two sends outstanding on a socket
  whole into its buffer and reports them sent: nothing is left queued for
  the next send to find or for the timeout to time. See "Send backpressure"
  in `docs/API.md`.) What
  this means for memory: per socket the engine can hold `wsBackpressureLimit`
  across sends, or the largest single message the application sends,
  whichever is larger. The engine does not cap the size of one message; an
  application that sends very large ones to peers it does not trust should
  bound them or lower `responseTimeoutMs`.
- **permessage-deflate offers** (RFC 7692 §7) with a repeated parameter, a
  value on `server_no_context_takeover` / `client_no_context_takeover`, or
  window bits written with a leading zero are declined (the connection opens
  uncompressed, and the next offer in the list is considered); they were
  accepted. A request with several `Sec-WebSocket-Extensions` lines has them
  read as one list; only the last line was read.
- **A compressed message that is not a deflate stream closes with 1007**
  (invalid payload data), not 1009 (too big), which is kept for a message
  that inflates past `maxDecompressedSize`. After either, the frames behind
  the failed message in the same read are no longer delivered.
- **Invalid UTF-8 fails at the byte that makes it invalid.** `F4 90`, `ED A0`,
  `E0 80`, `F0 80` and the lead bytes `C0`, `C1`, `F5`-`F7` were rejected
  only when the sequence completed; Autobahn cases 6.4.2 and 6.4.4 go from
  non-strict to OK.
- **Text messages are validated faster.** Between multi-byte characters the
  UTF-8 check now takes ASCII eight bytes at a time instead of one. Measured
  on Linux as the instructions the engine itself executes (callgrind, the
  plain build, epoll, 1.1.21 against this release): echoing a 64-byte text
  message, 1815 to 1453; receiving a 64 KiB text message and sending it to
  51 sockets, 561,000 to 162,000. Nothing changes in what is accepted.
- A response with status 426 has the reason phrase `Upgrade Required` (it
  was `OK`).
- **`wsBackpressureLimit` bounds what is queued for a socket that has been
  shed.** From 1.1.16 to 1.1.21, once a socket's shed was pending (it is
  delivered on the next loop turn) every `wsSend()` returned `false` but was
  still queued, so the replies to one read of small messages from a peer that
  reads nothing were all held: 63 kB received held 150 MiB (macOS; 139 to 141
  MiB on Linux on all three transports, plain and TLS), for up to
  `responseTimeoutMs`. 1.1.15 held 2.1 MiB. `wsSend()` now returns `false`
  without queuing while the shed is pending and the queue has not drained
  (1.4 to 3 MiB held). A slow client that is still reading and is shed no
  longer receives the sends made between the shed and its Close(1013).
- **Frames for a WebSocket whose peer has reset the connection are dropped**
  instead of being held until the transport reports the failed write; the
  close (1006) is queued and `onWsClose` arrives on the next loop turn.
  Four connections sending 63 kB each peaked at +603 MiB on libuv and
  io_uring (1.1.21; 1.1.15: 5 MiB) and at 1.1 to 3.3 MiB now. Epoll was not
  affected. A send in that turn may still return `true`.
- **A frame header no longer reserves its whole declared length.** A 14-byte
  header declaring 16 MiB and one payload byte reserved 16 MiB of address
  space for as long as the connection stayed open; under `ulimit -v` 600
  connections ended the process with `std::bad_alloc`. The full reserve now
  waits until a sixteenth of the message has arrived. Cost: the parser's own
  instructions are unchanged up to 256 KiB, +1.75% at 1 MiB and +4.3 to 4.8%
  at 4 to 16 MiB; a whole 16 MiB echo costs +0.76%.
- **A compressed send (and inflate) of 4 GiB or more was silently
  truncated**; the input is now fed to zlib in pieces of at most 1 GiB.
- **Messages of 32 KiB or more are written without being copied into a frame
  first, and a large binary message is delivered as an ArrayBuffer over the
  memory it was received into** (see "Performance"). With
  `wsDeflate.sharedCompressor`, a message sent to many sockets in a row is
  compressed once (the bytes on the wire are unchanged; up to 256 KiB of the
  last message and its output are kept per server).
- Autobahn: 517 cases over TLS with compression on epoll and io_uring, and
  the plaintext and TLS+deflate suites on the final tree, no failed case.

## Linux transports and libuv

- **A read of freed memory at shutdown is fixed.** Reproduced under
  AddressSanitizer on 1.1.11, 1.1.16 and 1.1.21 (not on 1.1.10, whose epoll
  transport was built differently). A response written from `setImmediate`
  that took the queued path - one with a pipelined request waiting behind
  it - was noted for completion at the loop's next turn; if its connection
  was closed in that same turn (`close()` during a graceful shutdown), the
  connection was freed first and the loop then read its state byte. In
  practice the byte
  still said "closed" and nothing followed; had the memory been handed to a
  new connection in between, that connection's write queue would have been
  completed out of turn. A connection that closes now takes its pending
  completion with it.

- **`close()` from inside `onWsClose` no longer aborts the process on the libuv
  transport** (macOS, Windows, Linux with `MORO_ENGINE_TRANSPORT=uv`). For a
  WebSocket the engine itself was closing (a peer that stopped reading, which
  `responseTimeoutMs` closes, or a failed write), the callback's `close()`
  closed the connection and the engine then called `uv_close` a second time:
  `uv_close: Assertion '!uv__is_closing(handle)' failed`. Any WebSocket peer
  could trigger it in an application that shuts down when its last socket is
  gone. Present since 1.0.0. Not affected: epoll and io_uring.
- **`listen()` on a server that is listening, has stopped listening or is
  closing throws `EINVAL` on every transport.** On epoll (since 1.1.10) it
  replaced the listener and aborted at `close()`; on io_uring (since 1.1.6)
  both ports accepted and `close()` never finished; `close()` then `listen()`
  in the same tick left a listener nothing closed, and `worker.terminate()`
  never returned. libuv already threw. A retry after a failed first
  `listen()` still works.
- **At the descriptor limit the event loop no longer spins.** A peer holding
  the process at `RLIMIT_NOFILE` pinned a core per loop thread (io_uring,
  since 1.1.6: 73 ticks in 1 s with nobody waiting, 81 to 97% of a core with
  peers waiting; epoll, since 1.1.10, once the spare descriptor was taken: 78
  to 85%); now 0. Accepting pauses and resumes at the next sweep or when one
  of the server's own connections is freed; on io_uring a peer arriving at
  the limit is turned away within a sweep (1 s at most). On the libuv
  transport (Linux, `MORO_ENGINE_TRANSPORT=uv`) the listener was the same: it
  is now the engine's own and pauses and resumes as the others. macOS does
  not spin.
- **io_uring: a worker thread whose server could not have a ring no longer
  aborts the process when it ends** (`MORO_ENGINE_TRANSPORT=uring`, ring
  creation failing in that thread; since 1.1.10).
- **io_uring: a ring that stops taking submissions at run time is torn down
  from the loop**, never from inside the call that met the failure. It used
  to abort the process (callbacks ran inside `respond()`), leave peers hung,
  kill the listener or leave `close()` unfinished (since 1.1.6). Peers are
  closed, callbacks fire once, and listening servers keep their socket and
  continue on epoll.
- **io_uring: what one connection is served per turn of the loop is bounded
  at 64 KiB, as on epoll.** A peer that sent without pause delayed timers
  and other connections (lag of 0.1 to 1.7 s measured; 1 to 29 ms now).
- **io_uring: a connection reset together with its last bytes is closed
  within a second.** It stayed open, and a WebSocket stayed open indefinitely.
- **epoll: what the server had received from a peer before that peer reset
  its connection is delivered before the reset is acted on**, as on the
  other transports (none of it was delivered before; now all of it, in 20
  of 20 runs on each transport). What the peer had not yet sent when it
  reset is lost on every transport: its own kernel discards it. On Windows
  the reset also discards what the server's kernel had received and the
  engine had not yet read (a reset flushes the connection's queues there,
  as RFC 9293 section 3.10.7.4 describes), so nothing of it can be
  delivered.
- **libuv (macOS, Linux `uv`): one read of at most 64 KiB per connection per
  loop turn**, as on epoll. A peer flooding small WebSocket messages delayed
  timers by up to 433 ms (Linux) and 379 ms (macOS); now 1 to 20 ms. On
  Windows, where libuv reads through completion ports, the same bound is
  kept by stopping the stream in its read callback and starting it again on
  the next loop turn (`uv_read_stop`, `uv_read_start`). That path was run
  on macOS and Linux through a test switch (full suites, both TLS
  libraries, AddressSanitizer; timer lag 1 to 18 ms) and on Windows CI,
  where restarting from the loop's check phase first left a stream waiting
  for the next timer, so the restart is made from an idle handle.
- **libuv: whether a connection's output is backed up** (which pauses reading
  pipelined requests behind it) is counted by the engine from its own pending
  writes, on every platform, instead of read from libuv.
- **Windows: `write()` and `wsSend()` stop reporting room once a client has
  reset the connection.** They reported room for every piece written to it
  until the loop next ran, so a handler streaming while `write()` returned
  true copied and held all of it, and `responseBackpressureLimit` and
  `wsBackpressureLimit` saw none of it. On Windows the engine now counts
  those writes itself until their callbacks run. Not affected: macOS,
  Linux.
- **io_uring and epoll: the descriptors a transport keeps per thread** (the
  ring, its eventfd, the spare descriptor for the descriptor limit) **are
  returned when the last server on that thread closes**; a later `listen()`
  sets them up again (21 descriptors before and after on every transport,
  where they stayed until the thread exited).

## Release binaries and build

- **The Linux glibc binaries load on glibc 2.28 and later.** Every published
  linux-gnu binary from 1.1.13 to 1.1.21 needed `_dl_find_object@GLIBC_2.35`
  (and some 2.34 and 2.32 symbols), so Debian 11, Ubuntu 20.04 and the RHEL 8
  family did not load them (RHEL 9, Rocky 9 and Amazon Linux 2023 carry a
  backport of that symbol and did). The linux-gnu release and CI jobs now
  build in pinned `manylinux_2_28` images (AlmaLinux 8, glibc 2.28) with the
  same clang 18.1.8, flags, CPU baselines and profile-guided optimisation,
  through `tools/linux-gnu-build.sh`, which fails the build if any binary
  needs glibc above 2.28 or any `GLIBCXX_` version. The binaries need at most
  `GLIBC_2.25`. Smoke tests succeed on AlmaLinux 8, Rocky 9, Amazon Linux 2023
  and Debian 11 (Node 20 and 24), where a build on a newer glibc fails on all
  four (the published 1.1.13 to 1.1.21 binaries already loaded on Rocky 9 and
  Amazon Linux 2023, which carry a backport); the arm64 binaries of both TLS
  variants also load, and `probe()` returns ok, on Ubuntu 20.04.6 LTS (glibc
  2.31) under Node 24.22.3. Request cost is within 0.5% of the previous build (A/A and B/B noise
  measured).
- **musl binaries are profile-optimised again.** They had been built without
  it (Alpine's clang had lost compiler-rt); a strict CI job now fails the
  build if it happens again.
- **Windows binaries are built with MSVC profile-guided optimisation**
  (`MORO_PGO_WINDOWS` in `release.yml`, with a strict CI job). Windows had
  none.
- **The training for profile-guided optimisation covers WebSocket (including
  permessage-deflate), HTTP/2, TLS request shapes and handshakes, request
  bodies, realistic header sets and the io_uring transport**, in separate
  processes merged by weight, and each Node ABI is built from a profile
  trained under a Node of that ABI. Before, the WebSocket phase never
  upgraded (its handler answered 404), HTTP/2 was trained only through the
  test suites, permessage-deflate and io_uring not at all, and one profile
  was reused across ABIs (on Node 26 the profile of the hottest binding
  functions, `Respond` and `End` among them, was discarded for a hash
  mismatch).
- **The bundled BoringSSL is link-time optimised, and its TLS layer
  (libssl) is built from a training profile of its own**: HTTPS requests run
  15 to 20% fewer instructions, and a new TLS connection 2% fewer. The
  libcrypto assembly kernels were already in use.
- **On Linux arm64, calls into node and libc no longer go through PLT
  stubs.**
- **The engine keeps its per-thread state behind one thread-local pointer**,
  so the addon's thread-local block (56 bytes, mostly the C++ runtime's; 553
  before) fits glibc's static TLS for libraries loaded at run time and every
  thread-local access is a few instructions instead of a resolver call. The
  linux-gnu build now fails if a binary's thread-local segment is over 256
  bytes and names the largest thread-locals. musl has no guard (its loader
  never gives a loaded module static TLS).
- **The bundled BoringSSL in linux-gnu binaries is built with
  `-fstack-protector-strong` and fortified libc calls** (the engine's own code
  had both; BoringSSL had neither: 0 of 370 libcrypto objects). Binary size
  +1.2%; cost under "Performance".
- **The Linux binary that uses node's OpenSSL no longer exports the C++
  runtime it links statically: the release build exports 3 symbols.** The
  tree before this change exported 799, including `operator new` and
  `delete`, which bound to the system libstdc++. The BoringSSL binary already
  hid them.
- **Node headers and `node.lib` are pinned by checksum** (`NODE_DIST_SHA256`
  in `tools/build.mjs`): they were checked only against a SHASUMS file from
  the same server. The "verify SHA256SUMS" step fails on a binary that is in
  no manifest.
- **Release candidates (`X.Y.Z-rc.N`) publish under the npm dist-tag `next`
  and never move `latest`.** They used to fail at publish (`--tag` is required
  for a prerelease), and `release.mjs patch` at a candidate produced the wrong
  version. A post-publish step fails if `latest` moved. Testers install with
  `npm i @morojs/engine@next`.
- **The scheduled BoringSSL roll releases only when `main` is exactly the last
  release.** The Tuesday job released `main` as it stood, with a note saying
  no engine code changed: with unreleased work on `main` it would have tagged
  and published it and overwritten the release's hand-written changelog; at a
  release candidate it would have published the next patch to `latest`. It
  needs a non-prerelease version, HEAD equal to the commit CI verified and to
  origin's tag, and refuses to overwrite an existing note; otherwise it stops
  and opens its issue. Present since 1.1.20; its release path had not run.
- **A release waits for the whole CI gate** (`release.yml` calls `ci.yml`),
  so a red lane blocks it. The linux-arm64-gnu binaries, which no job loaded,
  are now smoke-tested on an arm64 runner and `conformance-linux` runs on
  x64 and arm64.
- **Every third-party action in the workflows is pinned by commit; the CI and fuzz workflows
  have read-only tokens.** The HTTP/2 fuzz harness runs per commit and
  nightly.
- Build tooling gains `--pgo-library` and `--pgo-library-profile=F` in
  `tools/build.mjs` and `TRAINING_NODES` in `tools/pgo.mjs` (see
  CONTRIBUTING); additive.
- Not run before this release: real x64 runners, Docker on the arm64 runner
  and Windows hosts. The first CI run on them is the proof for the x64
  training and the Windows profile build. Node 20, 22 and 26 were built and
  tested on the final tree (smoke and the full suite, Linux arm64, epoll); the
  first CI run repeats this on real runners. Binaries in an old `build/` directory for ABIs other than
  137 are stale and are not tested or packed without a rebuild.

## Performance

All numbers are instructions per operation, counted with callgrind on Linux
arm64 (engine plus the libraries it calls, except where a row says
otherwise), one connection, epoll unless stated. They are not request rates.
They have two baselines, and the two sets of numbers are not additive.

Against the source tree as it stood before the changes below, plain
(non-profile-guided) builds, epoll, io_uring and libuv alike:

| Workload | Instructions |
| --- | --- |
| plain `respond()` | -13.9% |
| pipelined | -12.0% |
| static route | -2.5% |
| JSON POST | -13.0% |
| connection per request | -11.7% |
| HTTPS, BoringSSL | -2.1% |
| HTTPS, node's OpenSSL | -9.4% |
| h2c | -4.0% |
| WebSocket echo | -6.5% |

What produced them, each measured alone against the tree before it:

- HTTP/1.1: a registry cached per server instead of thread-local descriptor
  calls, empty snapshot strings not exchanged, header values validated a
  word at a time, ASCII checked 32 bytes per step, repeated route lookups
  removed, prepared-response heads kept rendered: 10 to 20% fewer
  instructions per JavaScript-answered keep-alive request (prepared GET
  -19.1%, pipelined -10.2%, JSON POST -11.1%, connection per request
  -9.7%), -48.1% on a 64 KiB string body, -22.0% on a streamed response,
  -13.7% on a static route with 30 headers. Wire bytes unchanged.
- HTTP/2: a response body waiting on flow control is no longer moved in its
  buffer at every WINDOW_UPDATE (1 MiB through 16 KiB windows: -81%
  cleartext and -79% over TLS in engine and copy instructions; -46 to -49%
  with the default window); HPACK decoded and request fields checked faster
  (-19% with browser-sized headers).
- WebSocket: ASCII and UTF-8 checked 32 bytes per step (16 KiB text echo
  -47%) and compressed text validated after inflating with the same check
  (16 KiB permessage-deflate echo -84%); with `sharedCompressor`, 64 KiB sent
  to many sockets 4.37M to 64k instructions per delivered message.
- TLS (BoringSSL): one redundant error-queue check per read and write gone,
  74 to 100 instructions per request.

Costs measured for the same changes: the BoringSSL stack protector adds about
380 instructions per HTTPS request (the -2.1% is net of it); the WebSocket
frame-header change and the transport changes are listed in their sections;
plaintext workloads moved by at most 0.3% elsewhere.

Against the profile-guided build of the tree before the second round of
changes (the one this release's binaries are compared with, measured on the
final tree):

| Workload | Instructions |
| --- | --- |
| plain | -6% (epoll; io_uring -3.6 to -5.5%) |
| static route | -7.5% (libuv -1.5%) |
| HTTPS GET | -22% |
| h2c | -14% |
| WebSocket echo | -17% |
| new TLS connection | -2.5% |

libuv and io_uring rows all improve.

What produced them:

- Request header fields are stored as one copy of the request head instead of
  two strings per field: about 30% fewer engine instructions for a request
  with 30 headers, 3 to 13% for typical requests.
- A connection that does not pipeline no longer sets up the 15 extra
  pipelining slots: about 20% fewer instructions for a connection carrying
  one request (two more allocations per new connection; keep-alive requests
  still allocate nothing).
- Thread-local access (above): about 4 to 5% fewer instructions per
  JavaScript-answered request on Linux glibc (`_dl_tlsdesc_dynamic` fell from
  140 instructions per request to 0).
- Response headers are assembled in about half the instructions (621 to
  316).
- TLS: small replies answered in one batch (pipelined responses, the replies
  to the frames of one WebSocket read) share TLS records: pipelined HTTPS
  -46% (BoringSSL) and -52% (OpenSSL), WSS echo of 16 frames per read -56%.
  Large streamed chunks are encrypted from the application's bytes (TLS
  stream -71%).
- HTTP: a response body of 16 KiB or more, each piece of a fixed-length
  stream, and a chunked write of 32 KiB or more are written from the
  application's bytes instead of being copied behind the head: a 1 MiB
  response copies 131k instructions before and 0.3k after; 1 MiB streamed as
  64 KiB chunks 518k and 0.6k; a 64 KiB body -70% in engine, copy and
  allocation instructions.
- WebSocket: messages of 32 KiB or more are written without being copied
  into a frame; a 1 MiB binary echo -47% outside JavaScript.
- HTTP/2: request bodies are no longer copied twice (281k to 145k
  instructions for a 1 MiB body).
- Build: profile training, BoringSSL link-time optimisation and PLT removal
  (see "Release binaries and build"): epoll TLS GET -20.5%, h2c -14.7%, h2
  over TLS -11.6% and WebSocket echo -16 to -18% against the previous
  profile-guided build before the other changes; 28 of 29 epoll workloads
  improved.

Costs: the changes in the second round cost at most +0.16% on io_uring and
+0.08% on epoll on plain builds; the Linux libuv static and parameter routes
read +0.28% and +0.11% under the new training. A number of rows are
bimodal in the measurement harness only (a collection of earlier requests'
body buffers landing inside the interval), not in the engine.

## Loader

- An installed copy no longer looks for a binary in `node_modules/build`:
  the local `build/` directory is read only in the engine repository.
- **A platform package stamped for another release, or found outside the
  installation, is not loaded.** A package stamped 1.1.5 beside a 1.1.21 meta
  package loaded and `probe().version` said 1.1.21; with the platform package
  missing, one in an ancestor directory's `node_modules`, on `NODE_PATH` or in
  `~/.node_modules` was loaded. The lookup is confined to the
  installation's own `node_modules` tree (npm, nested, hoisted, pnpm and
  global-store layouts still load); `probe().error` says what was refused.
  `MORO_ENGINE_BINARY` still selects a file.
- **`probe().binary`** (new) is `{ path, version? }`: the file that was loaded
  and the version of the platform package it came from.

## Not changed

- No subprotocol is selected, WebSockets have no idle timeout, there is no
  Ping API, and `Origin` is not interpreted.
- A 1xx status passed to `respond()` is sent as a final response (a client
  waits on HTTP/1.1; it is a stream error on HTTP/2), as Node's `http` does.
- `getBodyLent()` still hands out bytes the engine cannot see other holders
  of: an asynchronous `fs.write` or socket write still in flight when the
  response completes reads the next request's body (the engine cannot see
  raw-pointer holders). `docs/API.md` and `index.d.ts` now state the rule: no
  asynchronous operation may still hold the bytes when the response
  completes.
- A WebSocket message that never completes holds up to 16 MiB per connection
  (`docs/THREAT_MODEL.md` states the 16 MiB cap and that WebSocket
  connections are exempt from the receive sweep).
- A request id an application keeps for more than 2^32 requests is not
  protected from reuse.
- DHE suites are never negotiated on the OpenSSL binary either (the engine
  sets no DH parameters), so a list of DHE suites alone fails every TLS 1.2
  handshake; `docs/TLS.md` says so. On BoringSSL a DHE entry in a mixed list
  is dropped: the list is narrowed, never weakened.
- HTTP/3 is not part of this release.
