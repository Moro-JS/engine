# @morojs/engine 1.1.20

TLS is terminated by a bundled BoringSSL, and the bundled copy is kept current
by a release that makes itself.

Nothing to change to get it, and nothing to change to keep running: update,
and the default binary is the one that carries BoringSSL. A server behind a
proxy that terminates TLS (nginx, a load balancer) never touches a TLS library
and runs exactly the code it ran. A process whose OpenSSL is specially
configured (FIPS mode, an OpenSSL config or provider option) keeps Node's
OpenSSL without being asked, and so does a server whose TLS configuration
BoringSSL has no support for. Additive for callers: one export (`selectTls`),
one field on `probe()` (`tls`), one environment variable (`MORO_ENGINE_TLS`).
What behaves differently is listed under "What changes" below.

## Two binaries, one difference

Every platform package now carries two builds of the engine per Node ABI,
from the same source:

| Binary | TLS library | Loaded |
| --- | --- | --- |
| `..._<abi>_boringssl.node` | BoringSSL, inside the addon | by default |
| `..._<abi>.node` | the OpenSSL the running `node` exports — every binary up to 1.1.19 | when that OpenSSL is configured, when asked for, as the fallback |

`probe().tls` says which is loaded and why:

```js
{ library: 'boringssl', version: '0.20261105.0', date: '2026-11-05', reason: 'default' }
```

The choice is made when the binding is first loaded on a thread, in this
order:

1. `selectTls('boringssl' | 'openssl')`, before the first `probe()` or
   `serve()`. Asking for the other library after that throws
   (`MORO_ENGINE_TLS_LOADED`); a loaded addon cannot be swapped.
   `selectTls('auto')` makes no choice and leaves it to the next two rules.
2. `MORO_ENGINE_TLS=boringssl|openssl|auto` (`node` is accepted for
   `openssl`). An unknown value is an error.
3. `auto`: BoringSSL, unless Node's OpenSSL has been configured —
   `--enable-fips`, `--force-fips`, `--openssl-config`,
   `--openssl-shared-config`, `--openssl-legacy-provider` (command line or
   `NODE_OPTIONS`), `OPENSSL_CONF`, `OPENSSL_MODULES`, or FIPS mode on. Then
   OpenSSL, and `reason` names what was found.

Two more things keep an update from breaking a running setup, both only when
nobody named a library:

- **A BoringSSL binary that cannot be loaded** is replaced by the OpenSSL one.
- **A TLS configuration BoringSSL has no support for** — an Ed448 or DSA key,
  a CCM cipher suite, a brainpool group; everything OpenSSL accepted up to
  1.1.19 — is served by the OpenSSL binary. `selectTls('auto', ssl)` settles
  that when the binding is loaded (MoroJS 1.8.24 and later pass their
  `server.ssl` this way); otherwise the first `serve()` with `ssl` on a thread
  makes the same move, provided the thread holds nothing of the BoringSSL
  binary yet (no server, no other native function taken from the module).
  When it does, the error is thrown as it is, with `MORO_ENGINE_TLS=openssl`
  named as the way out. That is the case under MoroJS 1.8.23 and earlier,
  which then serve such an app from their Node.js fallback, as they do for
  any TLS configuration the engine refuses, and log that message.

In both cases `probe().tls` reports `reason: 'fallback'` and `fallbackReason`.
A library asked for by name is never replaced by the other one.

## Why

For what every TLS record costs. Measured through the MoroJS adapter at one
worker, CPU per request, runs interleaved on one machine (arm64 Linux):

| workload | OpenSSL binary | BoringSSL binary |
|---|---|---|
| JSON reply over TLS, 1–50 items | 16.7 µs | 15.1 µs |
| 10 KB echo over TLS (`lendBodies`) | 17.6 µs | 15.4 µs |

(Medians of five 8-second runs each, both binaries from this release, the
OpenSSL one being what 1.1.19 shipped.)

OpenSSL 3 pays for its provider architecture on every record; BoringSSL has
none. Requests that are not encrypted run the same code in both binaries and
cost what they did.

## Kept current without anyone remembering to

Bundling a TLS library moves a duty here: a fix made upstream reaches a server
only through an engine release. BoringSSL publishes dated snapshots
(`0.YYYYMMDD.N`) every two to three weeks and no advisories, so the engine
takes every snapshot and makes the release automatic:

- `tools/boringssl.json` pins the snapshot by tag and commit. A fetch that
  does not resolve to that commit is not built, and none of BoringSSL's source
  is in this repository.
- A scheduled workflow looks upstream every week. A newer snapshot is put
  through the entire CI gate on every platform **before** it is committed;
  green, and the workflow commits the pin, tags a patch release and publishes
  it to npm with no human step; red, and it opens an issue and publishes
  nothing. It can be started by hand.
- `tools/release.mjs` refuses to cut any release while a newer snapshot exists
  and the pinned one is more than 21 days old.
- A server that terminates TLS on a snapshot more than 180 days old emits one
  process warning, `MORO_ENGINE_TLS_STALE`, saying how old it is and that the
  fix is to update. Once per process, worker threads included;
  `MORO_ENGINE_TLS_AGE_WARNING=0` turns it off.

A scheduled release is not a claim that the previous snapshot was vulnerable.
It is how a fix nobody announced still reaches you within weeks. What it asks
of you is the habit Node.js already asks for: keep the package updated.

## What changes

- **TLS 1.3 session tickets arrive with the first response** instead of in a
  packet of their own after the handshake (one packet per connection fewer).
  A client that reads the ticket before sending anything will not see it until
  it has made a request. Resumption is unaffected.
- **BoringSSL has a narrower set of algorithms.** TLS 1.3: the two AES-GCM
  suites and ChaCha20-Poly1305 (no CCM). TLS 1.2 and lower: ECDHE and RSA key
  exchange, no DHE, CCM, ARIA or Camellia. A server *configured* with
  something outside that set (`ssl.ciphersuites`, `ssl.ciphers`,
  `ssl.ecdhCurve`, the key type) moves to OpenSSL by itself, as above. What
  cannot be seen from the configuration is a *client* that can only negotiate
  one of those — in practice a TLS 1.2 client without ECDHE, which is hard to
  find. A deployment that has one sets `MORO_ENGINE_TLS=openssl`.
- **Tickets do not carry between the two libraries.** Servers sharing
  `ssl.ticketKeys` resume each other's sessions when they run the same
  library; a ticket from the other one gets a full handshake.
- **Node's OpenSSL settings do not reach BoringSSL**: `openssl.cnf`,
  providers, engines, FIPS. That is what rule 3 above is for; a policy applied
  only through the system's default `openssl.cnf`, with none of those signals
  in the process, needs `MORO_ENGINE_TLS=openssl`.
- **Each platform package is larger**: two binaries per ABI where there was
  one, the new one about 2 MB more than the old (which is unchanged in size).
  One platform package is installed per machine, as before.

The default cipher policy is the same on both binaries and the same as
1.1.19: TLS 1.2 or later, the server's order, AES-128-GCM ahead of
AES-256-GCM, ChaCha20-Poly1305 for a client that lists it first. On a machine
without AES instructions the BoringSSL binary leads with ChaCha20.

## Licence

The engine's source remains MIT and entirely Moro's. The BoringSSL binaries
additionally contain BoringSSL (Apache-2.0); its licence text ships in every
platform package as `LICENSE-BORINGSSL`.

## Building from source

`node tools/build.mjs` builds both binaries; the BoringSSL one needs `git` and
`cmake` 3.22+ (and `nasm` on Windows). `--tls=openssl` builds only the other
and needs neither. `docs/TLS.md` has the whole design.

## Tested

On arm64, Linux (glibc; musl for the build, smoke and TLS suites) and macOS:
every suite against the BoringSSL binary and the TLS and HTTP/2 suites again
against the OpenSSL one - 325 and 79 tests on Linux, the same on macOS less
three Linux-only cases. The same on Linux under ASan and UBSan. Both binaries
built for all six Node ABIs; the PGO cycle trains on the BoringSSL binary and
applies the profile to both. The x64 and Windows builds are exercised by CI.

New suite `test/tls-library.test.mjs`, 25 cases, each in a process of its
own: selection by default, by environment, by `selectTls()`, by a configured
OpenSSL; both fallbacks, with a CCM suite and an Ed448 certificate served end
to end on OpenSSL after BoringSSL refused them; the refusals that must stand;
the stale-library notice, once per process across worker threads. The smoke
test loads both binaries, and `MORO_ENGINE_REQUIRE_TLS` makes a silent
fallback a failure in a lane that means to test one library.

The sanitizer build no longer enables UBSan's vptr check. It needs run-time
type information behind every vtable it meets, node is built without any, and
a `std::shared_ptr<v8::BackingStore>` control block binds to node's vtable:
every copy of such a pointer (`getBody()` since 1.1.18) was reported as an
invalid object.
