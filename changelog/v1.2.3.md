# @morojs/engine 1.2.3

Memory. A connection between requests no longer holds a parser and request
buffers, and an isolate can give back what its start-up left on the heap.
Nothing changes on the wire and no option is added. Two capability flags,
one export (`trimMemory()`) and one `probe()` field are new.

## A connection at rest holds no request state

`capabilities.restingConnections`.

The parser, the snapshot of the request a handler was given, the buffer for
input received while a response is in flight, the staging ring of batched
dispatch and the buffers responses are built and batched in belonged to the
connection: 1,376 bytes of structure on Linux, plus whatever capacity those
buffers had grown to, for as long as the connection was open. They belong to
a request. A connection now takes them from its server's pool when bytes
arrive and gives them back when it comes to rest: nothing received and
unparsed, nothing staged, no response being built or written, no request in
a handler's hands. A connection that has sent nothing yet, or only its TLS
handshake, is at rest as well.

- The connection structure is 480 bytes on Linux (it was 1,376), and an
  idle connection keeps no heap buffer.
- Measured on Linux, 100,000 held HTTP/1.1 keep-alive connections, one
  request each every four seconds: 136 MB less resident memory, plaintext,
  and 108 MB less over TLS.
- CPU per request on that load is unchanged (27.6 µs before, 28.1 µs
  after, three runs each, inside the run-to-run spread), and throughput on
  short requests, pipelined requests, JSON, TLS and HTTP/2 is within noise
  of 1.2.2. A thread serves one read at a time, so with handlers that
  answer before returning, one state serves every connection of the thread;
  up to 256 are kept after a burst of requests held at once, and the sweep
  brings the pool back to 32.

When the state is given back:

- At the end of the read that brought the request, when the handler
  answered before returning (and the response went out whole).
- For a response completed outside a read - a handler that answered later,
  a write the socket finished later - at the start of the server's next
  read, or at the sweep. Never from inside the call that completed it.

What keeps its state: a WebSocket (the handshake's headers and query stay
readable for the socket's life, and frames are corked in its buffer), an
HTTP/2 connection and the per-request connections of its streams, and any
connection with a request in progress, including one whose bytes are still
arriving.

What a pooled state still holds of the last request it served is what a
connection held of its own previous request: buffers that are emptied or
overwritten before they are read. `test/resting-connections.test.mjs`
alternates two connections over one state, a request with a query, a
header and a body against one with none of them, and compares every field
and the complete header list.

`probe().connections` is new: `{ open, resting }` for the servers of the
calling thread.

The libuv transport's `uv_shutdown_t` (80 bytes) is allocated when a
connection sends one, not with every connection.

## `trimMemory()`

`capabilities.memoryTrim`.

Gives back what the calling isolate's start-up left behind: one
memory-reducing collection of its heap (V8's low-memory notification) and,
on glibc, the allocator's free pages. A heap that has just loaded an
application holds about as much committed-and-free memory as live memory,
and keeps it while the process is quiet. Measured on a worker thread that
had loaded a framework and an application: 24.0 MB of heap before, 14.1 MB
after.

It is a synchronous collection: call it once per isolate after start-up,
not on a request path. The heap grows again as load needs it.
