# @morojs/engine 1.1.14

A WebSocket throughput release, with one allocation taken off the TLS write
path. Nothing on the wire changes; no export or capability flag is added,
removed or renamed.

## WebSocket: one write per read

Every frame a read buffer held used to be answered with its own `send()`:
a client that pipelines sixteen frames into one segment got sixteen
syscalls back, and the echo of a batch cost as much as sixteen single
echoes. `feedWebSocket` now corks the connection for the whole read, the
way `dispatchBatch` corks a pipelined HTTP batch: every reply the buffer
provokes - the echo of each data frame, a Pong, a Close - accumulates in
the connection's cork buffer and leaves in one write when the parser has
consumed the buffer. Replies keep their order. A Close frame inside a batch
is answered after the frames ahead of it and the socket closes once the
flush is out, through the same flush-then-close tail an HTTP batch ending
in `Connection: close` uses; frames after the Close are ignored as before.
Frames that arrived in the same segment as the upgrade request, fed from
inside an HTTP dispatch loop, are flushed by that loop's own tail, as they
were.

`wsSend()`'s backpressure answer and the Ping-flood cap count the bytes
corked for the current read as queued, since they leave with the flush.

Measured on a 4-worker local run (macOS, libuv transport), 256 connections,
64-byte text frames, 16 in flight per connection: 971K frames per second
against 257K on 1.1.13 with the same framework build, 3.8x. Plain echo (one
frame in flight) is within noise, 128K against 122K.

The upgrade also zeroes the connection's request id once the 101 is out.
The per-request bookkeeping that runs on a terminal frame erases that id
from the request registry, and `0` is the one value that can never name a
live request there; the stale id could in principle have named another
connection's request after the 32-bit counter wrapped.

## TLS: one ciphertext buffer per loop

A TLS reply encrypted into a fresh `std::string` on every response, a
malloc/free pair per reply. The ciphertext now goes into one buffer per
loop (`cipherScratch_`, released above 64 KiB), and the transport is handed
a view of it; the queued and corked paths copy what they must, the direct
`send()` copies nothing. `transportWriteView` is the view-based twin of
`transportWrite` that both the plaintext scratch path and the TLS path now
share.
