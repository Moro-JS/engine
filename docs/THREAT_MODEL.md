# @morojs/engine — Threat Model

This document is the starting point for an external security reviewer and the engine's own record of its security posture. It describes what the engine does to defend itself against hostile network input, maps each defense to the code that implements it, and — just as importantly — states plainly where it does **not** defend and what a deployment must therefore provide.

> **Status honesty.** No external security review has been performed yet. This document *prepares* for one; it does not assert that one has happened. See [Testing & assurance](#testing--assurance) and the M5/M6 gates in [`ROADMAP.md`](ROADMAP.md).

Related: [`SECURITY.md`](../SECURITY.md) (reporting policy), [`DESIGN.md`](DESIGN.md) (architecture), [`CONTRIBUTING.md`](../CONTRIBUTING.md) (the non-negotiable "parser code lands with a fuzz harness" rule).

---

## Attack surface

The engine's job is to turn **raw, untrusted TCP bytes** into a safe, bounded request/message object for a JavaScript handler, and to serialize the handler's response back onto the wire. Everything hostile arrives as a byte stream on an accepted socket. That stream is parsed in hand-written C++ with manual memory management (raw V8 handles + libuv), which is precisely the code a reviewer should scrutinize hardest.

### Trust boundaries

```
  ┌──────────────┐   raw bytes   ┌──────────────┐   parsed view   ┌──────────────┐   snapshot   ┌──────────────┐
  │  Network      │ ───────────► │  Protocol     │ ─────────────► │  V8 boundary  │ ──────────► │  JS handler   │
  │  (untrusted)  │   libuv TCP  │  parsers (C++) │   bounded,     │  (binding.cpp)│   by reqId  │  (app code)   │
  │               │   server.h   │  http_parser.h │   validated    │               │             │               │
  │               │              │  websocket.h   │                │               │             │               │
  └──────────────┘              └──────────────┘                └──────────────┘             └──────────────┘
     TB0: attacker      TB1: only bounded,       TB2: only a numeric reqId/wsId    TB3: app trusts the engine to
     controls every     spec-validated data      crosses into V8; stale ids         have bounded/validated the
     byte and its        crosses out of the       resolve to a safe no-op            data; app owns its own logic
     arrival timing      parser
```

- **TB0 — Network → libuv/socket engine (`src/server.h`).** The attacker controls every byte, how it is fragmented across TCP segments, and its timing. The socket engine accepts connections, feeds bytes to the parser incrementally, writes responses in request order, and enforces connection lifecycle/timeouts.
  On Linux 6.1+ the same engine may run on the **io_uring transport** (`src/uring.h`) instead of libuv streams — opt-in (`MORO_ENGINE_TRANSPORT=uring`), gated by a feature probe and self-test, never required, and identical above the transport seam. Three transport-specific properties matter to a reviewer: (1) receive buffers are **kernel-provided** (a registered provided-buffer ring, 16 KiB × 512 per loop thread): the kernel writes a segment into a buffer it chose, the engine parses straight from it and recycles the buffer immediately after dispatch — no code path retains a pointer into a receive buffer (the parser copies partial heads/bodies into its own storage, TLS copies into the memory BIO, WebSocket unmasks in place then copies), which the transport-parity and conformance suites exercise under both transports; (2) teardown is **shutdown, cancel, close**: a synchronous `shutdown(SHUT_WR)` puts the FIN on the wire, then one submission carries `IORING_ASYNC_CANCEL` by fd (resolving the recv) and `IORING_OP_CLOSE`, and a `Connection` is freed only when its close state is reached *and* every submitted SQE that names it has completed (`inflight == 0`), so a late completion can never touch freed memory; (3) what one connection is served in one pass of the loop is bounded, as it is on the epoll transport (one 64 KiB read per socket per turn): a multishot receive completes for as long as its socket has bytes, so a connection with more than 64 KiB of completions counted in one pass has that receive cancelled, the completions already posted for it copied aside in order, and its socket read by the loop itself, one buffer per turn, until a read finds it empty - a peer that sends without pause shares the loop with its timers and the other connections instead of holding it; and a reset that reaches a socket together with the last bytes before it, which a multishot receive on a `DEFER_TASKRUN` ring does not report, is found by the sweep (a `poll` of each socket that has received anything since the last one), so the connection is closed within a sweep of the bytes being delivered. (The libuv transport has the same bound, on Windows too: a stream is read once per loop turn, where libuv would read it up to 32 times.) The ring's SQ/CQ are private anonymous mappings; a peer cannot influence which buffer is selected or observe another connection's data.
- **TB1 — Socket → protocol parsers (`src/http_parser.h`, `src/websocket.h`).** The parsers are pure state machines (no I/O, no dependencies beyond the C++ standard library) so they can be unit-tested and fuzzed standalone. They are the primary memory-safety and protocol-correctness surface. Only bounded, validated data is allowed to cross out of them.
- **TB2 — Parser → V8 boundary (`src/binding.cpp`).** The only handle that crosses into JavaScript is an integer `reqId` (HTTP) or `wsId` (WebSocket). The binding resolves it back to a `Connection*` through a registry; a stale id resolves to `nullptr` and every accessor is a safe no-op.
- **TB3 — V8 boundary → JS handler (app code).** The handler receives a batched, already-validated request snapshot. Application logic (auth, injection, business rules) is **out of scope** for the engine (see [`SECURITY.md`](../SECURITY.md)).

## Threats considered & mitigations

Every mitigation below cites the code that implements it. Where a defense is partial or absent, that is stated here or in [Known limitations](#known-limitations--non-goals).

### 1. Memory-safety bugs in parsing (over-read / overflow / UAF)

Hand-written C++ parsing of attacker-controlled bytes is the highest-risk surface.

- **Incremental, bounds-checked state machines.** `HttpParser::parse` (`http_parser.h`) and `WsParser::consume` (`websocket.h`) consume bytes against explicit state enums and length counters; any byte of a header or frame may arrive in a separate call, and the parsers persist partial state (e.g. WebSocket `maskPos_` persists across `consume()` calls so a payload split anywhere still unmasks correctly). Payload/length reads are gated on "do we actually have this many bytes buffered" checks (`available < contentLength_`, `available < chunkRemaining_ + 2`, `cont >= n - i` for truncated UTF-8 sequences) before any access.
- **Failed-parser latch.** Once `WsParser` returns `false` it stays failed (`failed_`), so a caller cannot be tricked into feeding more bytes into a corrupt state.
- **libFuzzer + ASan/UBSan.** Both parsers ship libFuzzer harnesses (`test/fuzz/fuzz_http_parser.cc`, `test/fuzz/fuzz_websocket.cc`) that feed arbitrary bytes in randomized split sizes and assert the parser never crashes, over-reads, or hangs. `test/fuzz/run.sh` builds them with `-fsanitize=fuzzer,address,undefined -fno-sanitize-recover=all`, so **every fuzzed input is checked by AddressSanitizer and UndefinedBehaviorSanitizer.** See [Testing & assurance](#testing--assurance).

### 2. HTTP request smuggling / desync (RFC 9112 §6, §11.2)

`finalizeHeaders()` in `http_parser.h` implements the spec-mandated rejections (these are treated as hard requirements in `CONTRIBUTING.md`, not best-effort):

- **`Content-Length` + `Transfer-Encoding` together → reject (400).** If a `Transfer-Encoding` header is present and a `Content-Length` is also present, the request is rejected (RFC 9112 §6.1/§6.3.3).
- **Conflicting duplicate `Content-Length` → reject (400).** Every `Content-Length` is parsed; a second value that disagrees with the first is rejected (RFC 9112 §6.3.5). Empty or non-digit `Content-Length` is also a 400.
- **`Transfer-Encoding` other than `chunked` → reject (400).** Only `chunked` as the (final) transfer coding is accepted; anything else fails.
- **Whitespace before the header colon → reject.** `parseHeaderLine` validates the field name with `isTokenChar` (RFC 9110 §5.6.2), so a space/tab before the `:` — a classic smuggling/obs-fold vector — makes the name a non-token and the line is rejected (RFC 9112 §5.1). Header lines that begin with whitespace (obs-fold continuations) are rejected for the same reason.
- **Strict request-line and HTTP-version validation.** The method must be all token chars; the version must match `HTTP/1.<DIGIT>` exactly (else 400), and a non-`1` major version returns 505.
- **Host discipline (RFC 9112 §3.2).** An HTTP/1.1 request with zero `Host` headers, or any request with more than one, is rejected 400 in `finalizeHeaders()` before routing can see it — absent/duplicate `Host` is a building block for host-confusion and cache poisoning behind a `Host`-routing proxy. (HTTP/1.0 without `Host` remains legal.) So is a request whose `Host` value is not `uri-host [ ":" port ]` (RFC 9110 §7.2): a reg-name or a bracketed IP-literal, then optionally a colon and a port of digits only. Whitespace, `/`, `?`, `#`, `@`, `\`, a comma-separated second host, a non-ASCII byte and a second colon outside brackets are all 400 (`validHostValue`), so an application that reads the value as a hostname never sees a path, a userinfo part or two candidates in it. Names are not otherwise judged: underscores, a trailing dot, an empty port and an empty value pass.
- **Request-target and field-value byte hygiene.** The request target and every header value are rejected (400) if they carry raw control bytes (C0 other than HTAB in values, or DEL) — a bare CR mid-line, NUL, or ESC would otherwise be surfaced to the app verbatim (log injection / downstream desync). High bytes (raw UTF-8) stay tolerated and absolute-form targets pass through opaquely, both matching Node. An opt-in `maxUriSize` answers 414 for over-long targets.
- **Strict chunked framing.** Chunk sizes are hex-validated (`1*HEXDIG` from the first byte of the line: no sign, no prefix, no leading whitespace), each chunk's trailing CRLF is required, and the terminating `0`-chunk + trailer are parsed explicitly (RFC 9112 §7.1). Every line of the framing must end in CRLF — the chunk-size line, the last chunk, each trailer line and the blank line that ends the body. The bare LF accepted as a line end in the request line and the header fields (§2.2) is not accepted here: a server that takes it inside chunk framing disagrees with an intermediary that does not about where the body ends, which is what request smuggling needs. A chunk extension is not interpreted, but a control byte in it (other than HTAB) is a 400. A chunk-size line is bounded at 16 KiB up to its LF (400), by one rule that does not depend on how the line was split across reads. Trailer lines are checked as header lines are (a token name, a colon, a value without control bytes) and then dropped: trailers are never merged into the headers. The trailer section as a whole is bounded by `maxHeadSize` (431), counted on the section itself and not on a pipelined request that follows it in the same read.
- **A rejected request ends the connection's input.** `HttpParser::parse` returns `Error` once and for every call after it, taking no further bytes, and the connection stops reading as HTTP the moment the error response is written or queued (`Connection::inputClosed`) — which can be well before it is flushed, when it waits behind responses the peer has not read, or behind a handler that is still running. Nothing sent after a rejected request is read as the rest of it or as a new request, and a connection gets one error response. The last response of a connection (`Connection: close`, HTTP/1.0) ends its input in the same way from the moment it is queued (`Server::closeOnceFlushed`): a request that arrives while it drains is dropped like one that arrives during the lingering close after it, not answered behind a response that said `close`.

> **Reviewer note (integer handling):** both length paths reject *inside* their accumulation loops. The chunked path checks `sz > maxBodySize` inside the hex loop; the fixed-length path checks `parsed > maxBodySize` after each `parsed = parsed*10 + digit` step, so the accumulator is bounded by `10*maxBodySize + 9` per iteration and cannot wrap `size_t` to a small value (which would desync the body length → request smuggling). Covered by regression tests: a 30-digit `Content-Length` is rejected 413 with the handler never invoked (`test/http-parser-unit.cpp`, `test/limits-conformance.test.mjs`).

### 3. Header / body denial-of-service (oversized requests)

Configurable limits in `HttpLimits` (`http_parser.h`), enforced during parsing:

- **Request head (request line + all headers):** `maxHeadSize` (default 64 KiB). Exceeding it returns **431 Request Header Fields Too Large**. Which status a head that is both over the limit and malformed gets is settled line by line, the same way in every parse path: 431 for a line - malformed or not - once the head up to and including it is over the limit, 400 (414, 505) for a malformed line while the head is still within it. So the answer does not depend on how the bytes were split across reads or on what a read holds behind the line.
- **Header count:** `maxHeaders` (default 100). Exceeding it returns **431**.
- **Body:** `maxBodySize` (default 10 MiB), enforced for both `Content-Length` and chunked bodies (accumulated across chunks). Exceeding it returns **413 Content Too Large** — for a chunked body at the size line of the chunk that would take it over, before any of that chunk is buffered, so a request in progress never holds more body bytes than the limit. The buffer for a `Content-Length` body follows the bytes received, not the length the head declares: it is reserved in full once a sixteenth of the body has arrived (at once for a body of up to 64 KiB), so a head and one byte of body do not set the declared size aside. The framing of a chunked body — size lines, extensions, CRLFs — is not part of the body and is not kept: whenever the parser has to wait for more input it drops what it has consumed from its buffer (once 16 KiB of it has accumulated), so what a request in progress holds is its body so far plus the input not parsed yet, however many bytes of framing the peer wraps around each body byte.
- **Configurable at `serve()`:** every limit is read from the JS options object in `binding.cpp` (`Serve`) — `maxBodySize`, `maxHeadSize`, `maxHeaders`, `idleTimeoutMs`, `requestTimeoutMs`, `maxConnections`, `maxPendingBytes`, `wsMaxMessageSize`, `wsBackpressureLimit`, `writeHighWaterMark`, `backlog`. The values above are defaults, not caps; nonsensical values (e.g. `maxHeadSize: 0`) are ignored in favor of the default.

### 4. Slowloris / slow-drip connection starvation

- **Idle sweep timer (`server.h`).** `listen()` starts an unref'd periodic timer (`onSweep`) whose granularity adapts to the configured timeout (capped 4 s, floored 250 ms). Every sweep increments an `idleTicks` counter on each connection that is **not** actively running a handler and is not still being sent a response; `onRead` resets `idleTicks` to 0 on any received bytes. A connection idle beyond `idleTimeoutMs` (default 120 s; `0` disables) is closed. A connection with response bytes still queued is not idle, whether its handler answered later or before it returned: how long delivery may take, and what happens to a peer that stops reading, is `responseTimeoutMs` (below). Only when that budget is disabled does the idle timeout apply to such a connection (`capabilities.idleSparesDrainingResponse`; engines before 1.2.0 applied it to a response a handler gave before returning, and cut slow downloads at the idle timeout). The timer is unref'd so it never keeps the process alive on its own.
- This defeats the **classic** slowloris — open a socket and send nothing (or stop mid-request) — and caps keep-alive reuse of a silent connection.

- **Request budget (`requestTimeoutMs`, default 300 s).** Because `idleTicks` resets on *any* read, the idle timer alone is defeated by a slow-drip attacker trickling a byte per sweep window. The same sweep therefore also counts `requestTicks` against a per-request budget measured from a request's first byte that does **not** reset on activity; expiry answers 408 and closes. A TLS handshake in progress counts as mid-request, so handshake slow-drip is bounded by the same knob.
- **Response-delivery budget (`responseTimeoutMs`, default 300 s) — the receive-side defenses' mirror.** A peer that sends a valid request and then stops *reading* (or pins a zero TCP receive window) would otherwise hold its queued response bytes, kernel buffers, and fd forever: the terminal write never flushes, so `active` never clears and both receive timeouts skip the connection permanently. The sweep counts `writeTicks` while uv writes are pending; **any drain progress resets the counter** — the outbound queue shrank since the previous sweep, or a write completed. Queue shrinkage (not completion alone) is the load-bearing signal: one large `respond()` is a single `uv_write` that completes only when the whole body has drained, so a steadily-reading slow client (weak link, rate-limited download) would otherwise be shed mid-transfer despite continuous progress. Only a drain making no progress for the whole budget is hard-closed (no error response is attempted — the peer isn't reading). This also bounds a stalled WebSocket consumer that the app has stopped sending to, and a stalled close-frame flush. An opt-in `responseBackpressureLimit` additionally hard-caps the not-yet-flushed HTTP outbound queue (the HTTP mirror of `wsBackpressureLimit`), for deployments with bounded response sizes. **Honest residual (same semantics as nginx's `send_timeout`):** a peer that deliberately drains a token amount per sweep window keeps resetting the budget and can hold its response memory for `body / drip-rate`; `responseBackpressureLimit` bounds the memory and `maxConnections` bounds the fan-out. **On Windows the budget covers less:** Winsock reports a send complete once it has copied it into the socket's kernel buffer, and copies the first two sends outstanding on a socket whatever their size (Microsoft, "Design issues - Sending small data segments over TCP with Winsock"), so one or two responses or messages given to a peer that is not reading are held by the system, not queued in the engine, and neither this budget nor the backpressure limits see them; from the third outstanding send on the queue forms and they apply. An HTTP connection in that state is closed by `idleTimeoutMs`; a WebSocket has no idle timeout, and an application serving untrusted peers on Windows should cap what it sends in one message and close sockets that stop answering. A queued response also holds an engine-side copy of the body (~2× peak for one slow drain) — apps serving large payloads to untrusted clients should stream via `write()` chunks or set the cap.

> **Remaining by design:** WebSocket connections are exempt from the *receive* sweep (they may legitimately idle between messages; the delivery budget above still applies to their queued sends), and a handler that never answers holds its connection — response time before the first byte is the app's business. See [Known limitations](#known-limitations--non-goals).

### 5. WebSocket protocol attacks (RFC 6455)

`WsParser` (`websocket.h`) fails the connection on any of the following (each cites the RFC section in-code):

- **Unmasked client frame → fail (§5.1).** A client-to-server frame without the MASK bit set is a protocol error.
- **Reserved bits / reserved opcodes → fail (§5.2).** Any RSV bit set (no extension is ever negotiated) or any opcode outside `{0,1,2,8,9,A}` fails.
- **Control-frame limits → fail (§5.5).** A control frame (Close/Ping/Pong) with payload > 125 bytes or with FIN clear (fragmented) is rejected.
- **Fragmentation state machine (§5.4).** A continuation frame with no message in progress, or a new Text/Binary frame arriving mid-message, fails.
- **Length encoding (§5.2).** A 64-bit length with the high bit set, or a non-minimally-encoded extended length, fails.
- **UTF-8 validation (§5.6, §8.1).** Text-message payloads and Close-frame reason strings are validated with a RFC 3629 validator that rejects overlong encodings, surrogates, out-of-range code points, and truncated sequences. Text is validated as it arrives, with state carried across frames and reads, so multi-byte sequences split across fragments are handled correctly and a message fails at the first byte that cannot be part of valid UTF-8 (the first continuation byte is range-checked against its lead byte), not when the sequence or the message completes.
- **Close-frame body sanity (§5.5.1).** A 1-byte close body (a status code must be 2 bytes) is rejected.
- **Max message size.** `WsParser::Limits::maxMessageSize` (default 16 MiB) is enforced across reassembled fragments, checked in `commitLength()` **before** any allocation and written to avoid `uint64` overflow. The buffer for a message follows the bytes received, not the length a frame header declares: it is reserved in full only once a sixteenth of the message has arrived, so a header and one byte do not set the declared size aside.
- **Handshake validation (§4.2.1).** Only a `GET` over HTTP/1.1 with `Upgrade: websocket`, `Connection: Upgrade`, exactly one well-formed `Sec-WebSocket-Key` and exactly one `Sec-WebSocket-Version: 13` is upgraded. Another method, HTTP/1.0, or a repeated key or version line (§11.3.1, §11.3.5: which of two values is meant is ambiguous, and an intermediary may pick the other) is an ordinary request. With engine-side upgrades on, a handshake whose only fault is its version is answered 426 with `Sec-WebSocket-Version: 13` (§4.4).
- **Frames the server originates.** A Close sent through `wsClose()` is always a legal control frame: a status code that may not appear on the wire (§7.4) is replaced and the reason is cut to 123 bytes, so an application bug cannot make the server emit a frame a conforming peer must treat as a protocol error.
- **Handshake accept key.** Computed with clean-room SHA-1 + Base64 (`sha1.h`); SHA-1 is used only for the RFC 6455 §4.2.2 accept-key ritual, not for any security property that relies on collision resistance (documented as such in `sha1.h`).

### 6. Resource exhaustion / connection lifecycle

- **One request in flight per connection (`server.h`).** Responses are returned in request order (RFC 9112 §9.3). Behind a handler that answers later, the next pipelined request is not surfaced to JS until that response has fully flushed (`finishResponse`). A handler that answers before it returns has its response complete once it is framed, and pipelined requests behind it are answered in the same pass and written together — until the bytes waiting on the peer reach the write high-water mark (256 KiB): from then on no further request is parsed, staged or handed to a handler on that connection, what the peer sends is buffered under `maxPendingBytes`, and dispatch resumes when the queue has drained below the mark (`outputBacklogged`, `resumeHeld`). This prevents request interleaving, unbounded concurrent handler fan-out per connection, and a peer that pipelines requests while reading nothing from having every one of them answered into memory.
- **Backpressure.** Streaming `write`/`wsSend` report backpressure against a 256 KiB high-water mark and resume via `onWritable`, so a slow-reading client cannot force unbounded server-side write buffering silently (the app is told to pause). Independently of app cooperation, the `responseTimeoutMs` delivery budget (section 4) sheds any connection whose queued writes make no drain progress across the whole budget, and the opt-in `responseBackpressureLimit` hard-caps the outbound queue.
- **Deterministic cleanup on close.** `doClose` erases the connection from the `globalRequests`/`globalWebSockets` registries and the live-connection set, stops reads, and frees the `Connection` (and its `WsParser`) in the libuv close callback — or, on the io_uring transport, once the cancel and close completions have been reaped and no submitted operation references it. `Server::close()` iterates a snapshot of live connections and closes each, so no keep-alive socket keeps the loop alive after shutdown. A ring that stops accepting submissions at runtime is treated as dead: every connection on it is aborted through the normal abort path (callbacks fire once, from the loop and never from inside the call that met the failure), the ring is closed so that the kernel drops what it still held for those connections, and the servers that were listening on it keep their listening sockets and carry on on the epoll transport, as do later servers on that thread. **Out of descriptors** (`EMFILE`/`ENFILE`), every transport on Linux turns the peers that are waiting away through a spare descriptor (the engine makes the accept call there on the libuv transport too: a listener of libuv's own cannot be told to stop asking); where an accept could only fail again at once (io_uring, or the spare itself lost to another part of the process) they stop asking until the next sweep or until one of the server's own connections has closed, so an event loop held at its descriptor limit sleeps instead of spinning. (On macOS the kernel drops a connection whose accept fails for want of a descriptor, so nothing stays queued to be reported again.)

> **Hardened (v1.0):** bytes received while a response is in flight are now bounded by a per-connection `maxPendingBytes` cap (default `maxHeadSize + maxBodySize`; the connection is hard-closed on overflow), and a `maxConnections` cap drops accepts beyond the limit (0 = unlimited, matching Node's `http.Server` default). WebSocket sends are bounded by a 1 MiB write-queue cap (a consumer that has not drained an earlier send is shed with a 1013 close by the send that takes the queue over it; a single message is never shed for its size, see [Known limitations](#known-limitations--non-goals)). Per-server JS state (V8 `Global` callback/context handles) and the `Server`/`Connection` C++ objects are freed via deferred cleanup once every libuv handle is reaped — no leak across `serve()`/`close()` cycles. **Since then:** the sweep gained a per-request receive budget (`requestTimeoutMs`, 408 on expiry — a steady byte-trickle is now reaped) and a response-delivery budget (`responseTimeoutMs` — a peer that never reads its response is now reaped), plus an opt-in `responseBackpressureLimit` outbound-queue cap. **Lingering close** (1.1.6): after the last response of a `Connection: close` exchange the engine half-closes and keeps the socket open, discarding input, until the peer's FIN — the RFC 9112 §9.6 staged close that keeps a request the peer had already written from being answered with a RST. A peer that never closes holds that slot for at most `kLingerMs` (2 s, `Server::onSweep`); the input discarded meanwhile is read into the shared receive buffer and dropped, never buffered, so a byte-flood on a lingering connection costs the reads and nothing else. A plaintext WebSocket ends the same way once its Close frame is out (RFC 6455 §7.1.1), under the same deadline, so a peer that is still sending receives the Close instead of a reset. Lingering connections count against `maxConnections`, which is the intended bound for a peer that opens connections faster than it closes them. **Remaining:** `maxConnections` is opt-in (unlimited by default). See [Known limitations](#known-limitations--non-goals).

### 7. Use-after-free at the V8 boundary (stale reqId/wsId)

The only handle JS holds is an integer id; a response can be produced synchronously or much later (async), during which the request may have already ended or the socket aborted.

- **Registry indirection (`server.h` / `binding.cpp`).** `reqId → Connection*` and `wsId → Connection*` live in global registries. `connFrom`/`wsFrom` in `binding.cpp` call `Server::lookup`/`lookupWs`, which return `nullptr` when the id is absent.
- **Terminal removal.** A reqId is erased from `globalRequests` the moment its response finishes (`finishResponse`), on abort/close (`doClose`, `abortConnection`), and on WebSocket upgrade (the HTTP reqId is retired and a wsId is issued). A wsId is erased on close/abort.
- **Safe no-op on stale ids.** Every accessor and response function guards on `if (!c) return;` (or returns a benign default). The id is resolved after the call's other arguments have been read: reading them can run JavaScript (a `valueOf`, a `toString`, an array getter) that answers the request or closes its connection, and the call must then find nothing. `isAborted(reqId)` is implemented as "the id is no longer in the registry", which is exactly how a handler learns its request went away. So a handler that calls `respond()`, `write()`, `wsSend()`, etc. on an id that has already ended does nothing rather than dereferencing freed memory.
- **Handler exceptions are contained.** The binding wraps JS callbacks in a `TryCatch`; a throwing handler is logged to stderr and does not tear down the event loop or leave the connection in a half-open C++ state.

> **Note (id reuse):** `reqId`/`wsId` are `uint32_t` counters and come round after 2^32 requests (or upgrades) on a thread - about twelve hours at 100,000 requests a second. An id that is still registered is skipped when ids are handed out (`nextReqId`, `upgradeToWebSocket`). A pipelined request is given its id when it is parsed and registered only when its turn comes, possibly much later (behind a handler that has not answered, or a response its peer is not reading); if the number was handed to another request in between, that request keeps it and the waiting one gets a new id (`activateStaged`; `test/batch-dispatch.test.mjs` laps the counter in a test build). What the engine cannot cover is the application's own bookkeeping: an id it kept from a request that ended more than 2^32 requests ago may name a different request now.

### 8. HTTP/2 (RFC 9113, RFC 7541) — opt-in via `options.http2`

One connection carries many requests, and most of the protocol is machinery a peer can drive without ever making a request. `src/http2.h` is a pure state machine (no I/O, no V8), unit-tested, fuzzed, and run against h2spec.

- **Rapid reset (CVE-2023-44487) and control-frame floods.** Frames that cost the peer nothing and the server work draw on one budget per connection: `RST_STREAM` (4 units), `PING`, `SETTINGS`, `PRIORITY` and empty `DATA` frames (1 unit each), and `WINDOW_UPDATE` frames beyond what the connection has earned (1 unit each: two are free for every stream the peer opened and one for every 1024 bytes of `DATA` sent to it, with 16 on top, so a client that opens its windows again as it reads - twice for every `DATA` frame, say - is not charged); 2000 units of burst, refilled at 200 a second. A peer that outruns it gets `GOAWAY(ENHANCE_YOUR_CALM)` and the connection is closed. A frame that makes the server reset a stream draws on the same budget: 4 units when the application had been given the request (a window update of zero, `DATA` or `HEADERS` after `END_STREAM`, a `PRIORITY` frame of the wrong size or on itself - the request's worth of work is lost exactly as when the peer resets it), 1 unit otherwise (a malformed request, an empty `DATA` frame on a closed stream). Streams also count against `maxConcurrentStreams` (default 256; beyond it `RST_STREAM(REFUSED_STREAM)`).
- **CONTINUATION flood (CVE-2024-27316).** A header block is bounded in bytes (`maxHeaderListSize` + 4 KiB) and in frames (64 `CONTINUATION` frames, empty ones included); exceeding either ends the connection.
- **HPACK bombs and table abuse.** The dynamic table is capped at the advertised `headerTableSize` (4096) and a size update above it is a `COMPRESSION_ERROR`. The decoded header list is capped at `maxHeaderListSize` (default `maxHeadSize`) and `maxHeaders` (the `Host` line made from `:authority` is not counted): past either the block is still decoded, to keep the table in step, but nothing more is stored and the request is answered 431. Integers are bounded (2^30, five continuation bytes), string lengths are checked against the block, and Huffman padding and EOS are validated (RFC 7541 §5.2).
- **Request smuggling through HTTP/2.** Field names must be lowercase tokens; values may not contain a control byte other than HTAB, or DEL (what the HTTP/1 parser refuses), or carry surrounding whitespace; `host` and `:authority` may each appear once and must have the shape the HTTP/1 parser asks of `Host`; connection-specific fields (`connection`, `transfer-encoding`, `upgrade`, `keep-alive`, `proxy-connection`, `te` other than `trailers`) and unknown or misplaced pseudo-headers make the request malformed (`RST_STREAM(PROTOCOL_ERROR)`). `content-length` must be a single consistent number and must equal the bytes received. `:path` gets the request-target hygiene of the HTTP/1 parser. Pseudo-headers never reach the application; `:authority` is delivered as `Host`: in place of the value of a `Host` field that came with it (RFC 9113 §8.3.1: a server must not use `Host` when `:authority` is present), or as one when the request carried none. Both values are checked as the HTTP/1 parser checks `Host`, and neither may be empty: an empty `:authority` or an empty `Host` makes the request malformed. So does an `http` or `https` request with neither field, whatever its target (`OPTIONS *` included): such a target always has an authority and a client must send it in one field or the other (RFC 9110 §7.2), as HTTP/1.1 answers 400 to a request without `Host`. A request with another scheme may have no authority and is then delivered without `Host`. `cookie` fields sent separately (§8.2.3) are delivered as one, joined with `; `.
- **Memory.** A request body is bounded by `maxBodySize` per stream (413), and the bytes buffered for requests not yet dispatched are bounded per connection (the larger of twice `maxBodySize` and four connection windows): past that the connection-level window is not reopened, so a connection buffers at most that plus one connection window (40 MiB at the defaults). When the window is spent with no request able to complete, the newest unfinished streams are refused (`RST_STREAM(REFUSED_STREAM)`, which a client may retry) until the rest fit. A request a handler holds keeps its body until it is answered, so handlers that answer later can hold `maxConcurrentStreams` bodies of `maxBodySize` for one connection (lower either for untrusted clients). A stream's buffer follows the bytes received, not the `content-length` it declared: a declared length of up to 64 KiB is reserved at once, a larger one in full only once a sixteenth of it has arrived (the rule for HTTP/1.1 bodies and WebSocket messages), so 256 streams that each declare `maxBodySize` and send nothing set nothing aside. What a connection has reserved for bodies still arriving counts against the same bound as what it has received: past it a declared length is no longer reserved ahead, and the buffer grows with the bytes that arrive. Responses are bounded at the socket as on HTTP/1: once the bytes waiting on the peer reach the write high-water mark (256 KiB), nothing more the peer sent is acted on until they drain - flow control does not do this, since a peer may open its windows wide and not read - and what arrives meanwhile is kept up to `maxPendingBytes` plus one connection window, past which the connection is closed. Response bytes held back by the peer's flow-control windows are bounded by what handlers write, on at most `maxConcurrentStreams` streams, and in time by `responseTimeoutMs`: a connection on which none of them has gone out for that long is closed, whatever else it sends. `responseBackpressureLimit` counts only the socket's queue, not these bytes (a client with the protocol's 64 KiB default window would trip it on any larger response).
- **Flow-control arithmetic.** Windows are 64-bit internally; an increment of zero, a window past 2^31-1 and a peer exceeding the window it was given are the errors the RFC assigns them.
- **Slow streams.** An HTTP/2 connection is exempt from the idle timeout only while a handler holds one of its requests; streams left waiting for the rest of a request do not keep it alive.

**Residual:** there is no per-stream receive deadline separate from the connection's idle timeout, and no `SETTINGS` acknowledgement timeout. The implementation is new in 1.1.19 and has not had an external review.

### 9. A stale or tampered bundled TLS library (1.1.20)

The default binary carries BoringSSL. That moves two things inside this project's boundary that used to be Node.js's: **which code terminates TLS**, and **how fast a fix in it reaches a running server**.

- **Tampering with what gets built.** The snapshot is named in one reviewed file (`tools/boringssl.json`: upstream tag and the commit it resolves to). The build fetches the tag over HTTPS from the upstream repository and compares the resolved commit with the pin; a mismatch is refused before anything is compiled. Nothing of BoringSSL is vendored, so there is no in-tree copy to drift or to patch quietly. Binaries are built only in CI and published with npm provenance, as before.
- **Symbol confusion inside the process.** The host `node` exports OpenSSL under the same symbol names. BoringSSL is compiled with hidden visibility and linked with its archives excluded from the addon's dynamic symbol table (`--exclude-libs,ALL` on ELF; two-level namespace on Mach-O; link order ahead of `node.lib` on Windows), so every `SSL_*` reference in the BoringSSL binary binds inside the addon. (What it does leave open are BoringSSL's three optional allocator hooks, `OPENSSL_memory_alloc` / `_free` / `_get_size`: weak references that stay unbound unless the host process itself defines them, which node does not.) `probe().tls` reports the library actually in use, and the test suite asserts it per binary.
- **Staleness.** BoringSSL publishes dated snapshots every two to three weeks and no advisories; a fix there is invisible unless the snapshot is taken. Mitigations, in order of who they bind: a scheduled workflow takes every new snapshot, runs the whole CI gate against it on every platform before committing it, and releases to npm on green with no human step (red opens an issue; so does a main branch that is not exactly the last release - commits waiting for the next release, or a release candidate, are never published by the roll, and the pin then moves with the next release made by hand); `tools/release.mjs` refuses any release on a snapshot older than 21 days when a newer one exists; and at run time a TLS server on a snapshot older than 180 days emits `MORO_ENGINE_TLS_STALE`. What none of this can do is update a deployment that nobody updates — the same residual risk as an un-updated Node.js, now with the engine as the thing to update.
- **Loss of the operator's OpenSSL policy.** BoringSSL consults no `openssl.cnf`, provider, engine or FIPS setting. The loader therefore selects the OpenSSL binary by itself when the process shows any such configuration (FIPS mode, `--openssl-config`, `--openssl-shared-config`, `--openssl-legacy-provider`, `--enable-fips`/`--force-fips` - as flags, in `NODE_OPTIONS` or in node's configuration file - `OPENSSL_CONF`, `OPENSSL_MODULES`), and `MORO_ENGINE_TLS=openssl` or `selectTls('openssl')` selects it explicitly. A library asked for by name is never substituted. Residual: a policy applied through the system-wide default `openssl.cnf` without any of those signals is not detected — set `MORO_ENGINE_TLS=openssl` there.
- **Narrower algorithm set.** BoringSSL has three TLS 1.3 suites and no DHE/CCM/ARIA/Camellia. A configuration BoringSSL cannot serve - a TLS 1.3 suite it lacks, a cipher list none of whose entries it has, a group or a key type it lacks - is never silently reduced: with the library chosen by name it throws from `serve()`; with no library named the server is moved, whole, to the OpenSSL binary, which honours the configuration as written (DHE excepted: neither binary sets DH parameters, so a list of DHE suites alone fails every TLS 1.2 handshake on both) (`probe().tls` reports the move and its cause). A TLS 1.2 cipher list that mixes entries BoringSSL has with entries it lacks is served with the ones it has: a name a library does not know is skipped, by OpenSSL as well, so such a list is narrowed, never widened. A compliance profile is therefore either applied or refused, never weakened.

## Known limitations & non-goals

Stated plainly. Several of these are the reason the engine should sit behind a proxy for untrusted-facing production today.

- **TLS termination — new trust boundary.** The engine terminates TLS in-process via `serve()` `options.ssl` (`src/tls.h`): the TLS library is BoringSSL carried inside the default binary (pinned by tag and commit, fetched and built in CI, never committed here), or — in the second binary every platform also ships — the OpenSSL exported by the host Node binary (headers from the same Node version's tarball, so versions cannot skew); `docs/TLS.md` says which is loaded when, and threat 9 below covers what bundling changes. Either is driven through a memory-BIO pair so the TLS layer is a pure transform with no socket access. Hardening defaults: TLS ≥ 1.2 (configurable floor), renegotiation and TLS-level compression disabled, server cipher preference, config errors throw from `serve()` (a misconfigured TLS server never silently boots as plaintext). A TLS handshake in progress counts against the `requestTimeoutMs` budget (handshake slow-drip is bounded with no extra knob); plaintext or garbage bytes on a TLS port get the library's alert and a close. Close: best-effort `close_notify` on teardown (truncation signaling). Records the TLS library answers by itself, one answer each - a TLS 1.3 KeyUpdate that asks for one back, a TLS 1.2 renegotiation request refused with an alert - are answered for as long as the peer reads; a peer that sends them without reading is closed once 256 KiB of answers wait on it (`Server::tlsAnswer`), so it cannot have a byte queued for every byte it sends. Resumption: a session is resumed only by a context whose policy matches the one that issued it (protocol floor, cipher configuration, and on a server that asks for client certificates whether one is required and the set of CA certificates - `TlsContext::setSessionContext`), so servers that share `ssl.ticketKeys` but not a client-certificate policy, and the contexts before and after an `updateSsl()` that changed it, do not take each other's sessions. Not implemented: session resumption/tickets tuning, OCSP stapling, multi-identity SNI (one key/cert per server; SNI names are not dispatched). **The external-review gate below applies with extra force now that the engine parses TLS from untrusted peers — front with a proxy or review before exposing it raw.**
- **`permessage-deflate` (RFC 7692) — opt-in, off by default.** When *not* enabled it stays *declined* (no `Sec-WebSocket-Extensions` in the handshake; any RSV bit on the wire is a protocol error), preserving the compression-oracle-free default posture. When enabled via `options.wsDeflate`, inbound messages are inflated with a hard output cap (`maxDecompressedSize`, default `wsMaxMessageSize`) checked incrementally *before* allocation — a zip bomb hits close code 1009, not OOM — and text is UTF-8-validated after inflate (1007 on failure; 1007 as well for bytes that are not a deflate stream). Nothing behind a message that failed is delivered. An offer RFC 7692 §7 says to decline (a repeated parameter, a value on a flag, malformed window bits) is declined and the connection runs uncompressed. Enabling it is a deliberate app decision (the compression side-channel is why it's off by default).
- **HTTP/2 is opt-in (`options.http2`), HTTP/3 is out of scope.** See threat 8 for what the HTTP/2 implementation defends against. Not implemented there: WebSocket over HTTP/2 (RFC 8441), server push, CONNECT (refused), and priorities (parsed, ignored).
- **No built-in *rate* limiting.** Per-IP/per-tenant rate limiting is the framework's/operator's responsibility, not the engine's. A **`maxConnections` cap** IS available (drops accepts beyond the limit) but defaults to unlimited, matching Node's `http.Server`; operators facing untrusted traffic should set it (or cap connections at a proxy).
- **Per-connection memory is bounded.** Head (64 KiB), body (10 MiB), and WebSocket message (16 MiB) default limits bound a single request/message; the input received and not yet dispatched (the `pending` buffer together with what the parser still holds behind the requests it has handed over) is bounded by `maxPendingBytes` (default head+body), in total and not per response; HTTP responses waiting on the peer are bounded by the write high-water mark plus the one response that crossed it (no further request is taken from the connection until they drain — so the bound is set by the largest response the application gives, as it is for a single request; `responseBackpressureLimit` caps that too); WebSocket send backpressure is bounded by a 1 MiB write-queue cap across sends (`wsBackpressureLimit`; `0` disables — an operator raising limits owns the memory math). The cap does not bound one outgoing message: a single `wsSend()` to a socket with nothing queued is held whole, whatever its size, until the peer reads it or `responseTimeoutMs` closes a peer that stopped reading, so the largest message an application sends is its own per-socket bound for a stalled peer. Replies to one read's worth of small messages count as sends like any other: once the cap has shed a socket nothing more is queued for it, and a frame that finds the connection reset is dropped. A WebSocket message that is still arriving has no time budget (WebSockets are outside the receive sweep): a peer that sends all of a `wsMaxMessageSize` message but its last byte holds that much - 16 MiB by default - for as long as it keeps the connection open, at no further cost to itself, so the figure to size against is `maxConnections` x `wsMaxMessageSize`. Every one of these is run-time configurable via `serve()` options. The one un-capped-by-default axis is the *count* of live connections (see `maxConnections`, opt-in above).
- **No per-handler response deadline.** Receive-side slow-drip is bounded (`requestTimeoutMs`) and delivery-side slow-read is bounded (`responseTimeoutMs`), but a handler that simply never answers holds its connection — deliberately: response time before the first queued byte is the app's business, and reaping it would break long-polling/SSE by design choice rather than by operator choice.
- **WebSocket protocol-violation close:** the engine sends a Close frame before tearing the connection down (§7.1.7 SHOULD) — `1009` for an oversized message, `1007` for invalid UTF-8 payload data, `1002` for other violations — then, once it flushes, half-closes and reads until the peer's FIN or the 2 s linger deadline (§7.1.1; a TLS connection is closed after its close_notify), surfacing the same code to `onWsClose`. (A cleanly *received* Close frame is echoed per §5.5.1.)
- **Lenient line endings in the request head.** For the request line and header lines the HTTP parser splits on `\n` and strips an optional trailing `\r`, so a bare-LF line terminator is accepted there (chunked-body framing requires CRLF, above). This is a minor leniency relative to strict CRLF (RFC 9112 §2.2); a reviewer should consider whether it creates a parsing differential with a stricter upstream proxy.
- **Where the binary is loaded from.** The loader takes the platform package only from the `node_modules` tree its own package is installed in (beside it, nested under it, hoisted above it within that tree), and only at its own version; a package of that name in a `node_modules` above the application, on `NODE_PATH` or in `~/.node_modules` is not loaded, and neither are the binaries of another release. The current directory plays no part. Under Yarn Plug'n'Play and in a checkout of this repository the lookup is Node's own. `probe().binary` reports the file that was loaded; `MORO_ENGINE_BINARY` (named at start-up by MoroJS) replaces the lookup altogether.
- **No external security review yet.** See below.

## Testing & assurance

What backs the claims above today, and what's planned to deepen coverage next.

### Fuzzing

- **HTTP/2:** `test/fuzz/fuzz_http2.cc` drives the session and HPACK with a host that answers requests at once, later, or never, and that stops the session part-way through its input, which must change nothing but when things happen.
- **Differential:** `test/fuzz/fuzz_http_diff.cc` runs the same bytes through the HTTP/1.1 parser's three paths — the buffered state machine, the in-place scan with stored headers and the in-place scan that stores nothing, the two a server connection uses for a request that starts a read — whole and split, and aborts on any difference in status, error code, request or leftover bytes. `test/http-parser-unit.cpp` holds the deterministic version of the same comparison, at every split point of a fixed set of requests.
- **Harnesses:** `test/fuzz/fuzz_http_parser.cc` and `test/fuzz/fuzz_websocket.cc`. Each treats its first input byte as a chunk-size selector and replays the remaining bytes through the parser in randomized splits, exercising the incremental path (a header/frame byte can land in any `parse()`/`consume()` call). The HTTP harness also drives the keep-alive reset + pipelined-continuation path; the WebSocket harness asserts the parser stays failed after the first protocol error.
- **Sanitizers:** built with `-fsanitize=fuzzer,address,undefined -fno-sanitize-recover=all` (`test/fuzz/run.sh`), so ASan + UBSan check every input.
- **Seed corpora:** `test/fuzz/corpus/http` and `test/fuzz/corpus/ws` ship hand-authored seeds covering the interesting cases — smuggling vectors (`smuggle-cl-te.raw`, `smuggle-dual-cl-conflict.raw`, `te-not-chunked.raw`), whitespace-before-colon (`header-ws-before-colon.raw`), oversized head, chunked extensions/trailers, and (WS) bad opcodes, RSV set, unmasked text, oversized control frames, 1-byte close, and extended lengths.
- **Where they run:** every harness of `test/fuzz/run.sh` (`http`, `httpdiff`, `ws`, `http2`, `tls`, `pmd`, `uring`) runs for 20 s on every commit (`ci.yml`, `fuzz-smoke`) and for 10 minutes every night with a corpus that is kept between runs (`.github/workflows/fuzz.yml`; the corpus lives in the Actions cache and is minimized weekly into a 90-day artifact). Locally: `npm run test:fuzz`.

### Conformance suites

Wire-level suites that talk to the engine over raw TCP sockets (no `http.request`), so framing and connection lifecycle are asserted byte-for-byte:

- `test/conformance.test.mjs` — **39** HTTP/1.1 cases (the first 21 are the M1 gate; DESIGN.md records 21/21 passing), including request boundaries on a pipelined connection and clients that disconnect part-way.
- `test/conformance-edge.test.mjs` — **76** edge cases: request-line, field, `Host`, `Content-Length` / `Transfer-Encoding` and chunked-body syntax case by case, HTTP/1.0 clients, and the statuses without content.
- `test/limits-conformance.test.mjs`, `test/conformance-hardening.test.mjs`, `test/linger-close.test.mjs` — every limit at its boundary, the three timeouts, what one connection can make the server hold, and what happens to a connection after a rejected request.
- `test/ws-conformance.test.mjs` — **64** WebSocket cases; `test/ws-deflate-conformance.test.mjs` — **22** permessage-deflate cases.
- `test/run-h2spec.sh` — h2spec, the HTTP/2 conformance suite: **146/146** over TLS; 145 on a cleartext port, where the one difference is that bytes which are not the HTTP/2 preface are answered as HTTP/1.1.
- `test/http2.test.mjs` — **53** HTTP/2 cases against a real client (nghttp2 via `node:http2`) and hand-written frames; `test/http2-unit.cpp` — 41,650 checks, every bound of threat 8 at the bound and one past it, including HPACK decoding against 647 header blocks from an independent encoder.
- Standalone C++ unit tests: `test/http-parser-unit.cpp` (11,388 checks, among them the parser's three paths compared at every split point of a fixed set of requests) and `test/websocket-unit.cpp` (373,513 checks), run via `npm run test:unit`. (DESIGN.md's milestone entries cite the 91 and 183 checks they had at the time.)

### Sanitizer-clean builds

The parsers are pure, dependency-light state machines specifically so they can be built and run under sanitizers. The fuzz harnesses build clean under ASan+UBSan (above), and the C++ unit suites are held to sanitizer-clean status (DESIGN.md notes the WebSocket suite is "ASan/UBSan clean"); a reviewer can rebuild `test/*-unit.cpp` with `-fsanitize=address,undefined` to re-verify.

### Security posture & external review

The engine's parsers are pure, dependency-light state machines built for auditability, and they've been through substantial internal hardening: libFuzzer harnesses with seed corpora, ASan/UBSan-clean builds, a full threat-model pass, and focused security audits that found and fixed real bugs. It's designed and tested to handle hostile input safely.

As is standard practice for any software that terminates TLS for untrusted internet traffic, a formal independent security audit is recommended before the highest-assurance deployments.

## Reviewer quick-start

Audit these first, in order — this is where hostile bytes are handled:

1. **`src/http_parser.h`** — the HTTP/1.1 state machine. Focus on `finalizeHeaders()` (smuggling rejections + Content-Length parsing/overflow), the chunked body loop, and all the `buf_`/`scanPos_`/`consumed_` index math.
2. **`src/websocket.h`** — `WsParser::consume`/`beginFrame`/`finishExtendedLength`/`commitLength`/`finishFrame`, the unmask loop, and `isValidUtf8`.
3. **`src/server.h`** — the libuv read/write paths (`onRead`, `writeOut`, `onWrite`), the `pending`/pipelining logic, the idle sweep, and connection teardown/registry bookkeeping (lifetime correctness).
4. **`src/binding.cpp`** — the V8 boundary: `extractBytes`, `buildHeaders`, the reqId/wsId lookups, and the `TryCatch` handler containment.
5. **`src/sha1.h`** — clean-room SHA-1/Base64 (correctness of the handshake key).

node tools/build.mjs          # build the addon for the running Node ABI
