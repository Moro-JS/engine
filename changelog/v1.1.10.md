# @morojs/engine 1.1.10

A hot-path release: engine-answered routes (static and parameter) cost a
fraction of what they did per request - parsed in place, answered from a
cached frame, and not parsed at all when a keep-alive client repeats its
request - on a new epoll transport that is the Linux default; a registry
bug that could stall a server after enough idle connection closes is
fixed. Nothing on the wire changes, nothing in the API is added, removed or
renamed, and every capability flag is as in 1.1.9.

## Engine-answered routes: parsed and framed without the request machinery

1.1.5 (static routes) and 1.1.9 (parameter routes) kept a reply out of JS.
The request still went through everything a JS-bound request needs: a
request id and a registry insert/erase, the staging slot swap, two header
scans (`Upgrade`, `Expect`), and a fully materialized header list. Measured
with perf inside the harness container, the engine's own share of a
saturated core was 5.3%, with the HTTP parser the single largest item.

- **Route-first parsing.** The parser asks the server, right after the
  request line, whether this request will be answered inside the engine
  (`HttpParser::routeHook`: an engine route matches, nothing is queued ahead
  of the request on the connection, the connection is plaintext). When it
  will, the headers are parsed in *light* mode: every line is validated and
  the framing headers are interpreted exactly as always - `Host`,
  `Connection`, `Content-Length`, `Transfer-Encoding`, `Expect`, `Upgrade` -
  but none is lowered into a slot or copied. The stored header list is left
  untouched for the next request JS sees.
- **Framed straight from the parser.** `Server::answerFromParser()` writes
  the reply into the cork buffer from the route the hook matched, then
  resets the parser. No request id, no registry insert or erase, no snapshot
  swap. In request order: an engine route behind a staged JS request still
  takes the ordinary staged path, so a pipelined `[static, js, static]`
  batch answers in order and JS sees exactly its own headers.
- **Framing headers classified once.** `Expect: 100-continue` and `Upgrade`
  are recorded while the header lines are scanned (`expectContinue()`,
  `hasUpgrade()`), and `finalizeHeaders()` resolves the accumulated
  `Host`/`Connection`/`Content-Length`/`Transfer-Encoding` state instead of
  walking the list again. This removes two header scans and one full pass
  from every request, JS-bound ones included.
- **One append per reply.** A static route caches its complete wire frame
  for the common request shape (HTTP/1.1 keep-alive, not HEAD) - status
  line, Date, headers, Content-Length, blank line, body - and rebuilds it
  only when the Date cache ticks, once per second; the reply is then a
  single append into the cork buffer instead of the eight the frame builder
  makes. A parameter route caches the same head and appends only the length
  and the segment. Every other shape (HEAD, `Connection: close`, HTTP/1.0)
  is framed exactly as before, and the wire-parity matrix proves the bytes
  identical either way.
- **Cheaper byte validation.** The token-char and field-value checks the
  parser runs on every byte of a name, method and value are table lookups
  now, and the framing-header dispatch compares with `memcmp` on the
  length it already switched on.
- **`-fno-plt` on Linux.** The addon is linked `-z now`, so libc's
  `memchr`/`memcpy`/`memcmp` - each on the per-request path - are called
  through the GOT directly instead of PLT stubs.
- **No thread-local on the hot path.** The Date line cache and the shared
  receive buffer were `thread_local`; in a dlopen'd addon each access is a
  `__tls_get_addr` call through the dynamic linker (0.3% of a saturated
  core in the profile). Both now live on the `Server`, which is one per
  loop thread already.
- **PGO training matches the harness shape.** `tools/pgo-train.mjs` adds a
  closed-loop phase: 64 keep-alive connections, one request in flight each,
  over static, empty, POST and parameter routes. Release binaries were
  trained only on single-connection pipelined traffic before.

Measured on the arm64 Linux VM used for the harness work (two server
cores, zrk `--closed`, six generator threads, the raw `morojs-engine`
harness entry, the same gcc toolchain on both sides):

| | 1.1.9 | 1.1.10 |
|---|---|---|
| engine share of a saturated core (perf, `GET /`) | 5.43% | 3.58% |
| user space in total, syscall stubs excluded | 8.7% | 6.1% |
| dynamic linker share | 0.30% | 0% |
| `GET /user/0`, 64 connections (median of 4) | 386k req/s | 434k req/s |
| `GET /user/0`, 512 connections (median of 4) | 480k req/s | 505k req/s |
| median over all nine route × concurrency cells | 465k req/s | 484k req/s |

At 64 connections, the regime where the raw entry trailed the uWS-based
entries by about 10% on the same box, every route is 9–13% faster; at 256
and 512 connections 3–8%. The unoptimised gcc build of 1.1.10 outruns the
clang+PGO 1.1.9 release binary in seven of the nine cells.

## New transport: epoll, the Linux default

The profile of a saturated core left one item the request path did not
own: libuv's stream layer. Per connection it is an alloc callback, a read
callback, a write request and a handle close around the same `read`/`write`
syscalls the engine would make itself - 1.5% of the core, where uWS's own
loop spends 0.5% on the same work. The engine now has that loop.

`transport: 'epoll'` is one epoll fd per loop thread, surfaced to libuv as a
single `uv_poll` so the engine stays on Node's loop (the integration uWS
uses). Accept, receive and send are made directly on plain non-blocking
sockets; `EPOLLOUT` is armed only while a write is backpressured; a
connection closed inside a readiness round is freed from a `uv_check`, never
on the stack that closed it. Everything above the transport - the parser,
the cork, TLS, WebSocket, the sweep, the notify path - is the same code the
libuv and io_uring transports drive, and the whole suite runs in all three
lanes (`MORO_ENGINE_TRANSPORT=epoll|uv|uring`) with the wire-parity matrix
byte-identical across them.

Measured on the same VM and toolchain as the table above, `GET /` at 64
connections: the `node` (libuv) share of a saturated core went from 1.50%
to 0.2%, and total user space per request from 6.1% (this release on
libuv) to about 5.3%, against 7.1% for raw uWS and 8.7% for 1.1.9. In the
same session, over the harness's nine route × concurrency cells (two
rounds each), the raw `morojs-engine` entry on this build ran a median of
496k req/s against 464k for the raw uWebSockets.js entry, ahead in eight
cells and level in the ninth; the `morojs` framework entry on the same
binary ran 484k.

Selection, decided once per process: Linux runs epoll by default; libuv on
`MORO_ENGINE_TRANSPORT=uv` (and always on macOS and Windows); io_uring stays
opt-in (`MORO_ENGINE_TRANSPORT=uring`), and an io_uring request the kernel
or sandbox refuses now falls back to epoll, not libuv. `probe().transport`
reports `'epoll'`, `transportReason` the default/override note,
`transportMode` `'epoll'`. The `transport` and `transportMode` unions in
`index.d.ts` gained the new value; nothing else in the API changes.

## Fast lane: parsed in place, answered from the cache, repeats without a parse

With the request machinery and the stream layer gone, what remained of the
engine's share was the parser itself (1.8% of the core), the dispatch glue
around it and the copies between them. Three changes take the rest out of
the common case; none changes a byte on the wire, and every rejection,
framing rule and ordering guarantee of the light parse above still holds
(the same test file proves it).

- **Parsed in place.** A request that arrives whole in one read on an idle
  connection is scanned straight from the transport's receive buffer
  (`HttpParser::parseDirect`): the request line as always, the route hook,
  then - for an engine route - every header line validated and the framing
  ones classified exactly as `parseHeaderLine` does, without the copy into
  the parser's buffer and without lowering any name that is not the length
  of a framing header. A request JS will see is handed to the buffered path
  with its request line already parsed; a partial head or a body still to
  receive goes to the buffer with the state machine positioned where the
  scan stopped. Only a pipelined remainder is ever copied.
- **Answered from the cache, no dispatch.** `Server::fastLane` takes a read
  when nothing is queued on the connection in either direction (no active
  or staged request, no bytes waiting to be written, the parser idle). A
  complete engine-answered request of the common shape - HTTP/1.1
  keep-alive, not HEAD, nothing pipelined behind it - is framed from the
  route's cached frame and written at once, skipping the batch loops, the
  parse-for-more call and the flush bookkeeping. Every other outcome
  continues into the same dispatch as before, with the parse it already did.
- **Repeat-request memo.** The connection remembers the bytes of that
  request (up to 512 bytes) and the route that answered it. A keep-alive
  client that repeats it byte for byte - a poller, a health check, a load
  generator - is answered without a parse: one `memcmp`, the cached frame,
  one `send`. The memo is tied to a route-table generation that every
  `setStaticRoute`/`clearStaticRoutes`/`setParamRoute`/`clearParamRoutes`
  bumps, so a replaced or cleared route takes effect on the very next
  request, repeat or not; a JS-routed request in between leaves it valid;
  the Date line stays live through the frame cache. `test/light-parse.test.mjs`
  walks all of it on one socket: repeats, a JS route between them, a
  parameter route remembered in turn, two copies in one write (not a
  repeat: both answered, in order), a replaced route, a cleared table, a
  Date that advances across a second.
- **Fixed on the way: a replaced route's stale frame.** Re-registering a
  (method, path) with a new body left the route's cached frame in place
  until the Date cache ticked, so for up to a second the old reply went
  out. The cache is now dropped with the template.
- **Measured and rejected: sending a readiness round's replies in one
  burst.** The kernel profile put 23% of our server's CPU in waking the
  client per response (`sock_def_readable`) against 15% under fulmine.js
  with identical call chains, so holding each round's replies and sending
  them together was tried. It wakes the client less often but leaves the
  server idle until the clients answer the burst: 3-13% slower at every
  load. Replies go out as they are framed, as before.

## Fixed: request registry corruption after idle closes

The per-thread request registry (`flat_map.h`) uses key 0 as its empty-slot
marker. A connection torn down before it surfaced a request still carried
request id 0, and its close erased "key 0": the erase found the first empty
slot, shifted live entries into it and took the size counter below zero.
From then on every insert grew the table, doubling it each time, until the
process stalled in the rehash - about forty idle closes between requests
were enough. The registry now ignores key 0 on insert and erase.
`test/registry-idle-close.test.mjs` interleaves sixty idle closes with
requests and then fires a burst that must complete promptly.

  keep-alive socket (see above); on engine routes, Content-Length and
