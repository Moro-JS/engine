# @morojs/engine — Design

MoroJS's native HTTP engine: Moro-authored C++ with raw-V8 bindings (per-ABI builds, chosen for maximum performance including V8 Fast API calls), exposing a **Moro-shaped batched API** rather than a general-purpose server surface.

Goal: saturate the hardware (~105k req/s hello-world reference ceiling on the benchmark rig) with an API that needs **2–4 JS boundary crossings per request** instead of the ~10–20 a general-purpose binding needs.

## Architecture (three layers)

### L1 — Socket/event layer
- Integrates with Node's own libuv loop (`uv_poll` on the main loop; libuv ships with Node's headers and is the platform API).
- Three transports behind one seam (`TransportKind` per server, `src/server.h`). **epoll** (Linux, the default since 1.1.10): every listening and accepted socket is a libuv poll handle on the loop's own epoll, so one `epoll_wait` per loop turn delivers every event (1.1.11); accept, recv and send are made directly on plain non-blocking sockets, writable interest is armed only while a write is backpressured, and a socket is closed from its handle's close callback. The sockets a turn reports readable are served in that turn's check phase (`EpollLoop::serve`), grouped by the CPU their peer's packets arrive on (`SO_INCOMING_CPU`, read at accept and every 1024 reads) and by socket number within a group, the leading group rotating per turn (1.1.12): the kernel's readiness order says nothing about who is on the other end, and a peer that multiplexes many connections on one event loop then gets its replies back to back and wakes once per group instead of once per reply, a wake-up that is paid in this side's `send()` (see "epoll transport measurements" below). That grouping loses to arrival order when every request enters JavaScript under a generator that oversubscribes its cores, and no fixed run length between the two wins both, so 1.1.13 makes the order selectable (`MORO_ENGINE_SERVE_ORDER=grouped|arrival|auto`, grouped by default): `auto` has each loop measure the two orders (four alternating 200 ms windows, an 8% margin, two agreeing probes before leaving grouped) and serve with the faster one for a stay that grows with the margin and with repeated wins, re-probing as soon as the live rate moves 25% from what was measured or a quarter of the serving sockets' worth of new connections arrive in a second (`EpollLoop::tune`; `MORO_ENGINE_SERVE_DEBUG=1` logs the decisions). It is not the default: its gain is bounded to the JS-handler-under-oversubscribed-generator shape and, in fifteen-second runs, depends on where its first probes fall. **libuv streams** on macOS and Windows, or anywhere with `MORO_ENGINE_TRANSPORT=uv` (on Linux the listening socket of this transport is the engine's own too, watched by a poll handle, so that accepting can pause at the descriptor limit; a stream is read once per loop turn - libuv's second read of a turn, which it makes whenever the first filled its 64 KiB buffer, is declined on POSIX, and on Windows the stream stops reading and an idle handle starts it again once the loop has been round to its timers - so one connection's share of a turn is what it is on epoll). **io_uring** on Linux 6.1+ (`src/uring.h`, a hand-rolled ring with no liburing dependency), opt-in since 1.1.6 through `MORO_ENGINE_TRANSPORT=uring` (see "io_uring measurements" below for why it is not auto-selected). The ring is probed once per process at the first `listen()` — mandatory setup flags (`SINGLE_ISSUER | COOP_TASKRUN | TASKRUN_FLAG`; not `DEFER_TASKRUN`, which never wakes an epoll-driven loop), required features, opcode probe, a provided-buffer ring, and a socketpair self-test — and any refusal (`EPERM` under Docker's default seccomp profile, `ENOSYS` under gVisor, `EINVAL` on older kernels) silently selects libuv. One ring per loop thread, set up by the first listener on the thread and given back (ring, eventfd and spare descriptor closed) when its last listener and connection are gone, driven from the same libuv loop (`uv_poll` on the ring fd, `uv_prepare` flushes SQEs before the loop blocks), multishot accept and multishot recv into kernel-provided buffers (a connection with more than 64 KiB of completions in one pass is read by the loop itself, one buffer per turn, until its socket is empty), one in-flight `SEND` per connection, shutdown(2)-then-cancel-close on teardown (the FIN goes out synchronously, so the server still closes first on a `Connection: close` exchange). Byte streams are identical across transports (`test/transport-parity.test.mjs`); `probe().transport` says which one is live and `transportReason` why.
- Accept, per-socket state machines, corked writes, backpressure, idle/slowloris timeouts, graceful shutdown.
- **`TCP_NODELAY` is inherited, not set per connection**: the listening socket carries it (uv arm: `listen()`; epoll arm: `epollListen`; io_uring arm: `uringListen`) and Linux and XNU copy it to every accepted socket, which `test/sockopt-unit.cpp` verifies on the running kernel — one `setsockopt` less on every accept (Windows keeps `uv_tcp_nodelay` per socket).
- **The FIN rides with the last bytes of a `Connection: close` response, and the connection then lingers** (`tTryWriteLast`, `closeAfterResponse`). macOS: `TCP_NOPUSH` on, `send`, `TCP_NOPUSH` off, `shutdown(SHUT_WR)` — XNU does not run `tcp_output` when the option is cleared, and a `send(MSG_EOF)` under `TCP_NOPUSH` stays held too; the pending FIN is what pushes data + FIN as one segment. Linux: `send(MSG_MORE)` + `shutdown(SHUT_WR)`. So the peer can never close first: two segments a few microseconds apart let a fast client (wrk, oha) become the active closer and hold the TIME_WAIT, and on macOS, with no port reuse, a churning client then drains its 16k ephemeral ports (measured: 5.8k conn/s over 40 s; 27.5k after, ahead of Bun's 25.9k and uWS's 23.5k on the same harness). After the FIN the socket is **not** closed: it lingers with its input discarded until the peer's FIN arrives or `kLingerMs` (2 s, the sweep's granularity floor) passes — RFC 9112 §9.6's staged close. A client that writes its next request the moment a response completes, before it has seen the FIN (autocannon does exactly this), would otherwise have that request answered by the kernel with a RST, and a RST discards whatever of the response the client has not yet read. Measured with autocannon and `connection: close`: one error per connection and two reconnects per cycle before, none after. uWebSockets.js and node:http linger the same way; Bun.serve resets. Lingering connections count against `maxConnections` and are bounded by the deadline (THREAT_MODEL §6). A plaintext WebSocket ends the same way after its Close frame (RFC 6455 §7.1.1: half-close, read until the peer has closed, close), so a peer that is still sending when the server closes - a message over the size limit, `wsClose()` - receives the Close and its status code instead of a reset. **A TLS connection ends the same way** (1.2.4, `Server::tlsGoodbye` ahead of the FIN in `closeAfterResponse`): `close_notify` is written, then the half-close, then the same wait for the peer's FIN under the same `kLingerMs`. Until 1.2.3 it was `close_notify` and `close()`, and a peer still sending - the body of an upload answered 413, requests pipelined behind an HTTP/1.0 response that only the end of the connection delimits - had those bytes answered with a RST and lost the response it had not read; Node's own client tears its socket down on the failed write without reading what had arrived. The lingering connection's input is dropped before the TLS layer (`inputClosed` is tested ahead of `TlsSession::onCiphertext`), so nothing is decrypted, no alert of the peer's is answered, and a closing TLS connection can be held no longer and made to do no more than a plaintext one. The alert normally fits the socket in one write; when the socket takes only part of it the rest is queued, input is closed at once, and the FIN follows its completion under `responseTimeoutMs` like any last write. The server does not wait for the peer's `close_notify`: the peer's FIN ends the wait, or the deadline.
- Multi-core via SO_REUSEPORT: one engine per worker **thread** (MoroJS 1.9+, one process, shared code pages) or per worker process. A server still open when its thread's environment is torn down is closed by an environment cleanup hook (`capabilities.workerThreads`), so `worker.terminate()` never leaves libuv handles behind.
- **A loop turn has a time slice** (1.2.4, epoll transport; `EpollLoop` "time slice" in `src/server.h`). `settle()` serves a turn of fewer than 32 sockets (`kSliceCheck`) with the loop it had before there was a slice (`serveAll()`: no clock, nothing queued, one compare against `fastTurn` to get there). A turn of more is `serveSliced()`'s, which reads the clock once per 32 sockets served and stops at 50 ms (`kSliceMs`); the sockets not reached are put on `backlog` and the loop goes round. From then until nothing waits (`behind`, and `fastTurn` 0) every turn is `settleSliced()`'s, and `serveSliced()` queues what the poll phase reports instead of serving it: a socket not served in the turn before goes on `arrivals`, one that was goes on `backlog` (`WaitQueue`: a vector with a head index, a slot emptied when its connection closes, found through `EpollConn::waitSeq`). `settle()` then serves `arrivals` for half the slice - from the old end for the first half of that time (`pop`), from the new end for the second (`popNewest`) - and `backlog` oldest first for the rest, the oldest socket of each whatever the clock says. Three things keep a round over everything that waits short: the read shrinks with the number waiting (`quantum`: the whole 64 KiB buffer up to 256 sockets, proportionally less beyond, 1 KiB at least - what a service costs is what its read holds); the listener takes 1,024 connections a report instead of 64 (`kAcceptBatchBehind`), so a wave of connects is not accepted over seconds with the listen queue full meanwhile; and a waiting socket's watcher is stopped (`park`), because a level-triggered socket with unread bytes is reported by every poll of every turn - measured with 16,000 sockets waiting, the loop spent as long being told about them (48 `epoll_wait` calls of 1,024 events a turn) as serving. A stopped watcher wakes nothing, so an idle handle (`spin`) is active while any socket waits: the loop does not sleep, and the handle's callback arms the check so that every turn ends in `settle()`. Measured in a 2-CPU, 4 GiB container against 32,768 connections that each pipeline 10,000 requests at a time without reading: a new connection's request was answered in 5-7 ms before the flood, in 716 ms at the worst while the connections were all arriving, and in 65-130 ms once they had; before the slice it was not answered within 2 s for most of the flood. Why not a fair queue by connection, or a cap on requests per connection per turn: the first needs a cost estimate nobody has before a request runs, and the second is what `quantum` does where it matters (the bytes read) without touching a connection that is alone. Why the fresh end at all: under overload a queue served in arrival order answers everybody late; serving the fresh end answers the clients that are still waiting (the same reasoning as adaptive LIFO). Why the old end first, with one socket guaranteed: served after the fresh end, or in alternation with it, the old end has nothing in a turn whose first service uses the time up - with a new connection every 20 ms that brings 50 ms of work, a client that had connected earlier waited until the flood was over. Old end first, a waiting socket's place only moves forward, and when every service is a slice long the order is the order of arrival, as it is without a slice. The sweep, for its part, counts nothing against a socket that has waited since the sweep before (`keptWaiting`: `waitSeq` set, `servedTurn` older than the server's `sweepTurn_`): what its peer sent is in the socket unread, so there is no idle, request, stall or HTTP/2 window tick for it, and its counts go on with the first sweep after it has had a turn - a peer that always has a byte in the socket is measured by its turns. A waiting socket's write queue is pushed by the sweep (`epollFlush`: a stopped watcher reports no writability), and its delivery deadline then measures the peer exactly as it does on a socket that is watched. A connection nothing is read from any more (`inputClosed`) has its input discarded with `MSG_TRUNC`, sixteen buffers' worth a turn, instead of copied out and dropped: the first read that finds the input closed sets the connection's `recvFlags` (`epollDiscard`), so the reads of every other connection carry no test for it.

### L2 — Protocol engine
- HTTP/1.1: incremental SIMD-friendly parser; strict RFC 9112 (hard-reject conflicting Content-Length/Transfer-Encoding), header count/size limits, keep-alive, chunked bodies.
- WebSocket: RFC 6455 framing + permessage-deflate (zlib), Autobahn-validated.
- TLS: a linked library, never written here. Two binaries per platform and ABI since 1.1.20: BoringSSL carried inside the addon (the default; pinned and built by `tools/boringssl.mjs`), and the OpenSSL exported by the host node (FIPS/provider configurations, by request, and as the fallback). `src/tls.h` is the only file that knows there are two. See `docs/TLS.md`.
- HTTP/2 (1.1.19): RFC 9113 server + RFC 7541 HPACK in `src/http2.h`, a pure state machine like the HTTP/1 parser (no I/O, no V8). ALPN `h2` on TLS, prior knowledge on cleartext, HTTP/1.1 on the same port. A request on a stream is surfaced exactly as an HTTP/1 request is, so the binding and everything above it are protocol-blind.
- Out of scope: HTTP/3/QUIC.

- **A connection's request state is pooled, not owned** (1.2.3, `capabilities.restingConnections`; `ReqState`, `Server::wake`/`rest` in `src/server.h`). The parser, the snapshot of the request JS was given, the pending-input buffer, the staging ring and the cork and response-build buffers are one object that a connection holds only while it has a request: taken from the server's pool at the start of a read (`wake`), given back when the connection is at rest - a connection that is not HTTP/2 or a WebSocket, with nothing received and unparsed, nothing staged, nothing being built or written and no request in a handler's hands (`atRest`). The give-back happens only where no frame above reads the state: at the end of the read that brought the request (the synchronous case, which is every request of a handler that answers before returning), and for a response completed outside a read (a handler that answered later, a write the socket finished later) at the start of the server's next read or at the sweep (`queueRest`/`drainRest`). `sizeof(Connection)` went from 1,376 to 480 bytes on Linux and an idle connection keeps no heap buffer; measured, 100,000 held keep-alive connections cost 136 MB less. What a pooled state still holds of the last request it served is exactly what a connection held of its own previous request - buffers that are emptied or overwritten before they are read (`swapField`, `HttpParser::reset`) - so no request can see another's data that could not see its own connection's last request before. A thread serves one read at a time, so with handlers that answer synchronously one state serves every connection of the thread and stays in cache. WebSockets (the handshake's headers and query stay readable for the socket's life, and frames are corked in the state's buffer) and HTTP/2 connections and their per-request connections keep theirs. `probe().connections` reports the calling thread's open and resting connections. **What a pooled state may hold is bounded** (1.2.4, `Server::kRqKeepBytes`, 128 KiB of buffer storage by `ReqState::retained`): the buffers keep their capacity for the next request, and the peer sets how far the ones for the path, the query and the header fields grow - each up to `maxHeadSize`, in the parser, the snapshot and all sixteen staging slots, so one connection could leave megabytes in a state that the pool then kept for the life of the server. The test on the path of every request is free: the parser notes a head past 16 KiB (`HttpParser::kLeanHead`) in the comparison that used to be the `maxHeadSize` check alone (`headOver`), and `rest()` reads that note in the same load as the parser's state (`idleLean`). A state with the note is measured before it is pooled and freed when it is over the bound (`restLarge`); the sweep measures every pooled state (`trimRqPool`), which also catches growth by many heads under the mark, and when it brings the pool back from 256 to 32 it keeps the states holding least. The request objects HTTP/2 keeps for reuse are held to the same bound at the sweep (`h2TrimFree`). `probe().requestStates` reports the count and the storage.
- **What all connections hold together is bounded** (1.2.4, `capabilities.bufferBudget`; `Server` "Buffer budget", `BufferBudget` in `src/thread_state.h`). Per-connection limits do not add up to a bound: their sum over the connections a server accepts is more memory than a host has. Each connection carries the count of what it holds in buffers for its peer (`Connection::held`, from `heldBy`: capacities of the parser's buffer and body, kept input, the cork buffer, staged bodies, the transport's write queue; a WebSocket parser's reassembly buffer; an HTTP/2 session's `memory()`), summed per thread (`BufferBudget::held`) against the thread's share of a process budget - an eighth of `uv_get_constrained_memory()` or `uv_get_total_memory()` unless `memoryBudget` is set, divided by the threads with a server listening (an atomic count, looked at again at each sweep, since a cluster's threads start one after another), floored at the largest single message the thread's servers accept. The count is brought up to date by recomputing it for one connection at the places where it can have changed, not by instrumenting every append: the end of a read (`account`), a write queued or completed (`noteHeld`), coming to rest or closing (`release`). The recomputation is a walk over the connection's buffers, and it is taken at the end of a read only when there is something for it to find. A connection the read left at rest has nothing counted and pays nothing (`rest()` asks "nothing staged, nothing counted" with one load, `stagedOrCounted`) - that is every request answered within its read. One it left awake is walked when it holds bytes of its peer's or for it (`holdsHttp1`: a request partly received or pipelined behind another, a body, staged requests, a write queue, or an earlier count that may have changed); on HTTP/2 when the session says one of the figures its count is made of has moved (`h2::Session::moved`, set where kept input, a header block across frames, room for a body or a response behind a window grows or goes); a WebSocket at every read. A request without a body that a handler will answer later, a connection that has given its last response and waits for its peer's FIN, an HTTP/2 frame acted on where it was read: none of them changes a counted byte, and walking each cost an HTTP/2 request 75 instructions and a connection opened for one request 120. What that leaves to the sweep is the capacity a request state brought with it from the pool - storage the engine keeps, bounded there (`kRqKeepBytes`), nothing a peer has put in it; and the sweep recomputes every connection and re-bases the thread's total, so an update missed somewhere is an error of at most a sweep interval, never drift. The count is by capacity, which is what is allocated; what becomes of a connection is decided by content, because a buffer keeps the capacity an earlier request grew it to (a pooled request state, a WebSocket's reassembly buffer): `arriving()` is what the peer has sent and no handler has been given yet, `owed()` the response bytes it has not taken. Over the share, a connection whose read has just ended with more than 16 KiB arriving is closed (`shed`) when the thread is over its share even without that connection's own `owed()` bytes. Response bytes close nothing where they are queued (`noteHeld` only counts): at that moment nothing says whether the peer is reading, and a response to a peer that takes it must arrive whatever its size against the share, as it did before there was a budget - closing on queueing cut a 40 MiB response to a reading client after 2 MiB with a 16 MiB share. The budget therefore closes a connection in two places only, both on a clean stack: where its own read has ended, after everything the read brought has been dispatched (`account`), and after the sweep's pass. It never closes one from a write, a write completion or a handler's call, and never before the dispatch of a read's bytes; `doClose` itself ends a connection's input (`inputClosed`: every read path, the resume behind a drained queue and the error response stop there), stops its parser (`HttpParser::stop`: whatever is parsed for it afterwards, by a caller further up the stack, is an error, and the answer to an error stops at `inputClosed`) and drops the requests staged behind the active one, so that no path can hand a handler a request whose connection is gone. An HTTP/2 response held behind a window is counted where the read that brought its request ends, or where the handler's call returns when it answers later (`h2Written`). At the sweep, with less than an eighth of the share free, connections that have more than 4 KiB arriving or owed and have moved nothing for a whole interval (`Connection::stallTicks`, reset by every read, every completed write, a write queue that shrank since the sweep before and an HTTP/2 window opened for a held response - looked at whether or not `responseTimeoutMs` is set - and, for a connection with output queued that would otherwise be closed, by the kernel's count of that output not yet acknowledged (`tKernelUnsent`: `SIOCOUTQ` on Linux, `SO_NWRITE` on macOS, the same descriptor under TLS and on every transport; nothing on Windows) being lower than at the sweep before: the engine's queue moves only when the socket takes more, which on Linux is once a third of the send buffer is free, and a peer reading a few hundred kilobytes a second was closed for the size of that step. Two system calls per such connection, the sweep before the one that would close it and that one; a peer whose window is shut shows no decrease and goes on schedule) are closed unless a handler holds their request with nothing queued. That rule is what bounds responses nobody reads; a response that keeps moving is bounded per connection, as before, by what the application gives it and `responseBackpressureLimit`. Why close and not wait: a connection told to wait keeps its descriptor and a kernel receive buffer, a reservation by declared length lets a peer hold the budget by declaring and not sending, and without reservations every holder can be waiting for room at once. Measured in a 4 GiB container, 2 threads (256 MiB share each): 32,768 connections each sending an 889 KB form, a 4 MB multipart body or a 1 MB compressed body had 1.2.3 OOM-killed in under ten seconds; on 1.2.4 the container stays near 2 GiB (most of it the kernel's socket buffers, which have their own budget since 1.2.5, below) and a health check is answered throughout. The automatic budget is an eighth and not more because of what the count leaves out: the copy of a body a handler is given, what the allocator keeps, and those socket buffers. At a quarter the same floods left the container at up to 3.1 GiB, against 2.5 now.
- **`shrink_to_fit` does nothing on Linux** (found 1.2.5; `src/shrink.h`). libstdc++ implements `std::string::shrink_to_fit` and `std::vector::shrink_to_fit` inside `#if __cpp_exceptions`, and the engine is built with `-fno-exceptions`: every call compiles to nothing there, while libc++ and MSVC's library shrink. Every "do not pin a large buffer to an idle owner" in this file is therefore true on macOS and Windows only. `shrinkToFit` copies and swaps (and leaves a string alone when it could gain less than 64 bytes, which is the allocation rounding of some libraries); `test/shrink-unit.cpp` is compiled with `-fno-exceptions`, since a test built the usual way cannot see this. Found by comparing the allocator's figures with the budget's under a flood: queued writes were 549 MiB allocated for 284 MiB counted per thread. 1.2.5 uses the helper in two new places: `queueWrite` cuts a buffer to its contents when it holds a quarter more than them (a cork buffer grown by doubling, or one whose sent part was erased), and `epollCompactSent` drops the sent part of a queued write once at least half has gone and 64 KiB or less is left - never a large remainder, so a body being downloaded is not moved each time the socket fills. **The thirteen calls that were already there are unchanged, and so still inert on Linux**: the parser's input and body buffers, the response-build and cork buffers, the TLS record scratch, an HTTP/2 session's input, header-block and output buffers and a stream's body and pending response, a WebSocket's reassembly buffer, a response template's item list. What they keep is bounded - by the limits on what grew them, and for pooled request states by `kRqKeepBytes`, which frees a whole state and does not depend on this - and making them act puts a free and an allocation on the path of every upload, response and message over the 16 KiB watermark, on the platform where every benchmark of this engine has been run with them inert. That is a change to measure per workload before it is made, not one to slip in beside a memory fix.
- **Unread responses, far over the budget** (1.2.5; `Server::onPress`, `pressStart`, `heldFree`). The sweep's stall rule is a rule for a thread that is a little short; as a bound on responses it is slow (two sweep intervals) and blind to a peer that keeps sending (a read is "moving"). `charge()` starts a 250 ms timer when a thread holds `kPressAt` (2) times its share; each tick walks the server's connections, and for the ones owed more than `heldFree()` compares three figures with the last tick's (`pressSeen_`, a map that exists only while the timer runs, erased from in `doClose`): the engine queue plus the kernel's unacknowledged count, the session's `heldSent`, and `Connection::outMoved`, which `completeWrite` sets. No change at two ticks running puts a connection on a list that is closed largest first until `held <= limit`; the timer stops itself when the thread is within its share. The state is kept beside the connections and not in them because `Connection` is what a million idle connections cost; the one byte it needed sits in padding. `heldFree()` is the same idea applied to one exemption: 16 KiB of untaken response per connection before its intake is held (`outputBacklogged`, which on a thread over its share uses this figure and not the write high-water mark) is 512 MiB at 32,768 connections that no budget agreed to, so past the count at which half the share has 16 KiB each the figure is `limit / conns / 2`, floored at 4 KiB - computed only on the over-share path. The request side's exemption (`account`: 16 KiB arriving is never refused) was tried the same way and put back: it turned heads of ten kilobytes, which are ordinary, into 503s on a crowded thread, for 47 MiB a thread in the flood it was meant for. Measured in the 4 GiB container (32,768 connections): the zero-window flood 3.8 GiB before and 2.6 GiB now; the pipelining flood killed for memory in half the runs before, 2.7 to 2.8 GiB now.
- **The kernel's receive buffers have a budget too** (1.2.5, Linux, `capabilities.socketBudget`; `Server` "Socket budget"). The buffer budget counts what has been read; what has not is in each connection's kernel receive buffer, sized by the kernel (128 KiB to begin with), filled by the peer and charged to the process's cgroup. The measurements above were taken on a machine whose kernel-wide TCP memory limit (`tcp_mem`) happened to hold those buffers to 2 GiB; on a host with the memory to have no such limit in reach, the same floods put 2.9 GiB in socket buffers and the process was killed with the engine and the runtime at 0.5 GiB. The bound is on the buffer itself, because nothing else is enforced by the kernel at the moment the packet arrives: `BufferBudget::sockets` is the thread's share (twice its buffer budget), `BufferBudget::conns` its open connections, `roomy` how many fit with the system's buffer (`tcp_rmem`'s middle figure, read once). One comparison at accept (`conns > roomy`) is all an uncrowded thread pays, and no socket of it is touched - `SO_RCVBUF` ends the kernel's own sizing of a buffer for good, so it is not set until it has to be. Past `roomy`, `rcvTarget` is the largest power of two that fits `sockets / conns`, between 16 and 64 KiB: set on the accepted socket (`crowded`), on every socket of the server when the target has halved (`fitSockets`, at the accept that halved it - a pass over n sockets each time n doubles), and at the sweep on any socket that is not at the target (`refit`). Powers of two and a rule for raising - only when two steps of room have opened, to one step short - keep a count that moves about a boundary from setting every socket at every sweep; with no crowd a set buffer goes back to 128 KiB. The cost is deliberate and narrow: a sender does not split a segment to fit a window (`tcp_snd_wnd_test`), it waits for its probe timer, so a body larger than the buffer from a peer whose segments are larger than the buffer - the loopback interface, 64 KiB - arrives a buffer per probe, about five a second (1 MiB through 32 KiB buffers: 6.7 s; through 64 KiB or the system's: at once). The alternatives were weighed: counting each socket's queue and closing the largest is a system call per socket and acts at the sweep, long after a flood has filled the cgroup; a window clamp (`TCP_WINDOW_CLAMP`) is rewritten by the kernel's own sizing on several kernel versions; a smaller advertised segment size is fixed at the handshake and costs every loopback connection always.

### L3 — Raw-V8 binding layer (per-ABI, Moro-shaped)
- **Batched request snapshot**: one crossing delivers method/URL/query/headers as offsets into a single external ArrayBuffer. No per-header calls; no "request dies after the callback returns" hazard.
- **Single corked response write**: status + headers + body in one call — matches MoroJS's build-then-write-once response pattern. **V8 fast API calls** (1.1.6) on the hot calls (`respondPrepared`, `respondPreparedEmpty`, `writeHeadPrepared`, `write`, `end`, `endWith`, `isAborted`): an optimised caller reaches the engine's C++ directly, with no callback machinery. Their precondition is that no binding call can re-enter JS, which is why `onAborted`/`onWritable` are delivered from a `uv_async` on a later loop turn (`capabilities.asyncNotify`). The per-tag `v8-fast-api-calls.h` is fetched sha-pinned at build time (Node's headers tarball omits it) and the targets install only when the host V8 matches the compiled one.
- **Prepared response templates** (1.1.6): the fixed part of a response (status + app header block) is materialised once (`prepareResponse`) and replayed per request (`respondPrepared`) — byte-identical to `respond()`, minus the per-request header walk. **Static routes** (`setStaticRoute`) are a template plus a fixed body answered inside the engine before the request reaches JS.
- **Batched pipelined dispatch** (1.1.6, `capabilities.batchDispatch`): complete pipelined requests are parsed into a per-connection staging ring (16 slots; a `Connection: close` or `Upgrade` request ends the batch) and delivered in ONE `onRequestBatch(count)` call over engine-owned buffers — three `Uint32` per slot (reqId, method, interned path index) plus a control cell the engine advances as each synchronous response completes, so JS answers in order and stops at the first async handler (the rest are re-delivered when its response completes). Only the active slot's id is registered; static routes are answered by the engine inside the batch; the bytes match sequential dispatch exactly (`test/batch-dispatch.test.mjs`). A synchronous response is complete once it is framed, not once it is sent, so both dispatch loops check the connection's write queue before taking the next request: with `writeHighWaterMark` of response bytes still unsent, the batch ends there (the control cell says so), nothing more is parsed, and the write completion that brings the queue back under the mark resumes with the slots still staged. The check is one field read (`pendingWrites`) on a connection with nothing queued. `MORO_ENGINE_BATCH=0` restores one call per request. Gate (2026-09-11, M2 Ultra, wrk -c100, same binary, batch off → on, best of 3 / median): raw engine pipelined ×10 893.7k → 935.1k (+4.6%) / 881.0k → 915.5k (+3.9%), MoroJS-on-engine 887.2k → 935.0k (+5.4%) / 880.8k → 912.8k (+3.6%); plain 114.1k → 113.6k and 113.3k → 114.1k (within ±1%), CPU/req unchanged at 8.5 µs. The plan's bar was +5% on the median; the gain is consistent but sits just under it — the staging code ships behind the kill switch pending sign-off.
- **Stream hooks**: onWritable/tryEnd-style backpressure + native file streaming, shaped so the JS adapter can present real Node-stream semantics (write/writeHead/'finish'/'close'/'drain', pipe target).
- Body delivery: batched chunks; multipart parsing stays JS-side (shared MoroJS util).

### io_uring measurements (2026-09-11)

Same binary, same box, transport switched by `MORO_ENGINE_TRANSPORT`: Docker
Desktop VM (linuxkit 6.12, arm64, 8 vCPU), `node:24-bookworm`, seccomp
unconfined, `bench/transport-ab.sh --runs 3 --duration 10` (oha 1.16, median
of 3) and `bench/syscalls.sh` (strace -c). Numbers are relative, not absolute
(a VM on a shared host).

| shape | conc | libuv rps / p99 / CPU µs/req | io_uring rps / p99 / CPU µs/req |
|---|---|---|---|
| keep-alive | 64 | 171.5k / 0.75 ms / 5.83 | 199.0k / 0.41 ms / 5.02 |
| keep-alive | 256 | 194.6k / 2.15 ms / 5.11 | 166.7k / 1.81 ms / 5.99 |
| keep-alive | 512 | 179.6k / 4.17 ms / 5.53 | 181.4k / 3.51 ms / 5.48 |
| conn/req | 64 | 77.1k / 0.93 ms / 12.95 | 69.4k / 1.13 ms / 14.39 |
| conn/req | 256 | 78.1k / 3.51 ms / 12.77 | 64.4k / 4.44 ms / 15.49 |
| conn/req | 512 | 78.6k / 6.97 ms / 12.65 | 63.2k / 9.07 ms / 15.73 |
| fixed 20k rps | 256 | 20.0k / 1.13 ms / 15.45 | 20.0k / 2.07 ms / 22.03 |

Syscalls per request: keep-alive 2.02 (read + write) → 1.00 (sendto; recv is
multishot, ~0 `io_uring_enter`); conn/req 8.0 (accept4, epoll_ctl,
setsockopt, read, write, epoll_ctl, close, epoll_wait) → 3.0 (sendto,
shutdown, amortised enter). The syscall goal is met; the CPU is not: each
multishot completion costs a task-work round trip (`io_poll_wake` → task work
→ re-issue → CQE post → poll re-arm) that only amortises when many
completions land per loop turn, so io_uring wins at 64 and 512 keep-alive
connections and loses everywhere the batches are small - including the
fixed-rate cell, where it burns ~40% more CPU per request. Two bugs were
found and fixed on the way: `IORING_SETUP_DEFER_TASKRUN` never wakes an
epoll-driven loop (completions only materialise inside an explicit
`io_uring_enter`), and a close submitted at the end of a reap round loses the
FIN race to a fast peer on `Connection: close` (the peer inherits TIME_WAIT
and a churn load throttles itself on ephemeral ports: 24k vs 100k conn/s
until the transport `shutdown(SHUT_WR)`s synchronously). A later run with
`TCP_NODELAY` inherited from the listener (one `setsockopt` fewer per
accept) narrowed the churn gap to 85.4k vs 91.6k conn/s at c=64 and put
keep-alive c=64 at 247k vs 179k. Go/no-go (`transport-ab.sh` header): not met
→ libuv stays the default, io_uring ships opt-in with the full test matrix
behind it. Follow-ups that could flip it:
`DEFER_TASKRUN` behind a registered eventfd (task work batched inside our own
`enter`), ring-submitted sends batched per loop turn (`SUBMIT_ALL`), and
`IORING_RECVSEND_BUNDLE` on 6.10+. The full-framework Linux matrix on the
same VM (MoroJS-on-engine vs raw Bun.serve, both transports, worker-thread
clustering) lives in the MoroJS Benchmark repo, `candidates/2026-09-11/`.

Of those follow-ups, ring-batched sends were already in place (a SEND SQE is
only prepared at issue time; the reap loop's next `enter` submits every SQE
of the round, hence the 1.00 syscalls/req above), and `RECVSEND_BUNDLE` cannot
help a one-request-in-flight keep-alive shape (each recv completes with one
small request; there is nothing to bundle). `DEFER_TASKRUN` behind a
registered eventfd is implemented as the ring's first-choice mode (`uring.h`,
"Ring modes"; `probe().transportMode` reports which one is running):
completions stay queued as local task work until the engine's own
`io_uring_enter(GETEVENTS)` runs them as one batch, so the per-completion
round trip that cost the CPU above is paid once per wake. The 1.1.6 mode
remains selectable with `MORO_ENGINE_URING_TASKRUN=coop` for A/B runs.
These numbers predate the epoll transport: since 1.1.10 the Linux default is
the engine's own socket path on libuv's epoll, not libuv streams, and the
open comparison is epoll against io_uring on bare metal (`docs/ROADMAP.md`).

### epoll transport measurements (2026-10-08)

Same box as above (Docker Desktop VM, linuxkit 6.12, arm64), the server
pinned to two vCPUs and the load generator to the other six inside the
server's network namespace, engine-answered routes, every request parsed
and routed, medians of two interleaved rounds, thousands of requests per
second at 64 / 256 / 512 connections:

| generator | 1.1.11 | 1.1.12 |
|---|---|---|
| wrk, 6 threads, a new `/user/{n}` id per request | 393 / 458 / 517 | 494 / 641 / 683 |
| zrk, the web-frameworks harness settings (12 threads, fixed request) | 450 / 510 / 536 | 493 / 550 / 571 |
| uSockets' `http_load_test`, single-threaded, 40 connections | level | level |

Nothing in the server's own work changed between the two: syscalls per
request (2.0), `epoll_wait` per request, batch sizes and user-space CPU are
identical, and the server never sleeps under either. The whole difference is
one kernel symbol, `sock_def_readable`, the client's wake-up, which the
server pays inside its own `send()` and which ran from 17% to 34% of server
CPU depending only on the order replies went out in; the client's context
switches per request tracked it exactly (0.10-0.23). A client thread whose
replies arrive back to back wakes once for the group; interleaved with other
threads' replies it wakes once per reply. Serving a turn's sockets in
peer-CPU order is what makes the grouping deterministic. Tried and set
aside on the way: edge-triggered delivery (a private epoll fd with
`EPOLLET`, and `EPOLLET` applied to libuv's own registrations), which only
changes the order by accident and lands flat at ~450k at every concurrency
(ahead at 64 connections, behind at 512); a 1024-event drain batch (no
change); a sort by socket number alone (the full gain when the accept order
happens to group the client's threads, a 30% loss when it does not). A
single-threaded client is never asleep when a reply lands, so it sees no
change, and the VM amplifies the wake-up cost, so the bare-metal size of the
gain is the open measurement (`docs/ROADMAP.md`).

## Milestones (benchmark/conformance-gated)

- **M0 — bring-up** ✅: build driver + ABI matrix (115/127/131/137/141/147), probe() binding, packaging layout, CI skeleton, smoke matrix.
- **M1 — plaintext HTTP/1.1 core** ✅: accept/parse/keep-alive/batched boundary/route dispatch. Parser (`src/http_parser.h`, 91 unit checks), libuv socket engine (`src/server.h`), raw-V8 binding (`src/binding.cpp`). **Gate PASSED**: 21/21 HTTP conformance (`test/conformance.test.mjs`) and hello-world throughput at the benchmark rig's ceiling (engine ~86–91k req/s; MoroJS full stack on-engine ~78–80k).
- **M2 — streaming** ✅: writeHead/write/end with backpressure via libuv `onWritable` → drain, chunked transfer encoding, native Date/Content-Length, HEAD body suppression, Expect: 100-continue. Drives MoroJS SSE/range/sendFile middleware (verified by `tests/integration/engine-streaming.test.ts`).
- **M3 — TLS** ✅: in-process termination via `serve()` `options.ssl` — OpenSSL from the host Node binary (never vendored), a memory-BIO transform (`src/tls.h`), ALPN, and HTTPS+WSS conformance + hardening suites + `fuzz_tls_transport`. SNI multi-identity is out of scope (one key/cert per server). See `docs/ROADMAP.md`.
- **M4 — WebSocket** ✅ (protocol): RFC 6455 framing + handshake
  (`src/websocket.h`/`src/sha1.h`, 183 unit checks, ASan/UBSan clean), integrated into the engine (upgrade, ping/pong, close, binary+text) and MoroJS via `EngineWebSocketAdapter`. End-to-end verified with the `ws` client and `tests/integration/engine-websocket.test.ts`. permessage-deflate is shipped (opt-in via `options.wsDeflate`, off by default; `src/ws_deflate.h`).
- **M5 — hardening** ✅: libFuzzer harnesses + seed corpus for both parsers (`test/fuzz/`), nightly CI fuzz + sanitizer jobs, ASan/UBSan clean, idle/ slowloris timeout, functional load soak (no crash/hang/leak), `SECURITY.md` + `docs/THREAT_MODEL.md`. Found+fixed a Content-Length overflow smuggling bug during the threat-model pass. As with any TLS-terminating software, a formal independent security audit is recommended for the highest-assurance untrusted-facing deployments.
- **M6 — GA 1.0.0** ✅: the first published release — HTTP/1.1, WebSocket (+ permessage-deflate), in-process TLS, and fully runtime-configurable limits behind a stable surface. MoroJS ships the engine as its default (`engine: 'moro'`) with automatic Node.js fallback.
- **1.1.6 — the JS boundary and the toolchain**: deferred `onAborted`/`onWritable` delivery (never re-entrant from a binding call), prepared response templates + static routes, V8 fast API calls on the hot entry points, zero-copy string bodies through `String::ValueView` (Node 23+) with the Node 25/26 write API fixed, an environment cleanup hook that makes the engine safe inside `worker_threads`, HTTP/1.1 keep-alive responses without a redundant `Connection: keep-alive` line, an export-drift gate (`tools/check-exports.mjs`), and a PGO release toolchain (clang + lld, `tools/pgo.mjs`). Wire bytes are proven identical across every response path by `test/wire-parity.test.mjs`.
- **1.1.9-1.1.12 — engine-answered routes and the socket path**: parameter routes (1.1.9, `setParamRoute`), a route whose reply is one path segment answered inside the engine; static and parameter routes answered straight from the parser (1.1.10): scanned in place in the receive buffer, no request id, no header materialisation, the reply framed from the route's prepared head (rebuilt when the Date second changes) with one cached-frame append; the engine's own socket path on libuv's epoll as the Linux default (1.1.10), down to one `epoll_wait` per loop turn (1.1.11), serving each turn's sockets grouped by peer CPU (1.1.12). Measured in "epoll transport measurements" above and, against the field, in the MoroJS Benchmark repo.

## Packaging

esbuild-style: `@morojs/engine` meta package (loader + types) with per-platform packages as exact-version optionalDependencies:

```
@morojs/engine-darwin-arm64      @morojs/engine-linux-x64-gnu
@morojs/engine-darwin-x64        @morojs/engine-linux-arm64-gnu
@morojs/engine-win32-x64         @morojs/engine-linux-x64-musl
@morojs/engine-linux-arm64-musl
```

Each platform package carries two binaries per supported ABI:
`moro_engine_<platform>_<arch>_<abi>_boringssl.node` (BoringSSL inside, loaded by default) and `moro_engine_<platform>_<arch>_<abi>.node` (node's OpenSSL), plus `LICENSE-BORINGSSL`. ABI policy: 115/127/131/137/141/147 (Node 20/22/23/24/25/26); new Node major = one TARGETS line + CI run + minor release. The loader is libc-aware (glibc vs musl via `process.report`) and exports non-throwing `probe()` diagnostics that MoroJS's preflight consumes.

## Versioning

Independent semver. `0.x` through the milestones, `1.0.0` at M6.
New Node ABI → minor; rebuilds/fixes → patch; API break → major.
